# WORLD//ERROR — 11_WORLD_STATE.md

## Состояние мира

### Назначение документа

Этот документ определяет, что такое **состояние мира (WORLD STATE)**, как оно хранится, изменяется, проверяется и восстанавливается.

Состояние мира — это не история и не набор произвольных переменных.

Это **текущее фактическое состояние всех значимых сущностей и отношений мира**, полученное в результате событий.

Основной принцип:

> **EVENT изменяет STATE. STATE определяет, что существует сейчас. HISTORY объясняет, как мир к этому пришёл.**

---

# 1. Что такое WORLD STATE

WORLD STATE — это совокупность актуальных значений, описывающих мир в определённый момент времени.

Например:

* где находится NPC;
* кому принадлежит здание;
* открыта ли дверь;
* контролирует ли фракция территорию;
* существует ли определённый предмет;
* знает ли игрок о конкретном месте;
* находится ли персонаж в больнице;
* работает ли радиостанция;
* какие отношения между двумя фракциями;
* какой сейчас статус определённого расследования;
* доступен ли маршрут;
* сколько ресурсов находится на складе.

Упрощённо:

```text
WORLD STATE
    ↓
что существует
    ↓
где находится
    ↓
в каком состоянии находится
    ↓
кто чем владеет
    ↓
кто что знает
    ↓
кто с кем связан
    ↓
что сейчас доступно
```

---

# 2. STATE ≠ EVENT

Это фундаментальное различие.

### EVENT

Событие:

> «В 14:32 склад был захвачен».

### STATE

Состояние после события:

> `warehouse.owner = faction_B`

История хранит:

> «До захвата склад принадлежал faction_A».

Состояние хранит:

> «Сейчас склад принадлежит faction_B».

Поэтому:

```text
EVENT
↓
изменение
↓
STATE
```

А не:

```text
EVENT = STATE
```

---

# 3. STATE ≠ HISTORY

Мир должен хранить и текущее состояние, и историю его изменений.

Например:

```text
CURRENT STATE

Склад:
owner = faction_B
security = HIGH
access = RESTRICTED
```

История:

```text
Day 14
Склад построен.

Day 37
Склад передан faction_A.

Day 81
Произошёл конфликт.

Day 82
Склад захвачен faction_B.

Day 83
Доступ ограничен.
```

Игроку необязательно видеть эту историю целиком.

Но игровой движок должен иметь возможность восстановить происхождение текущего состояния.

---

# 4. Основной принцип хранения

Не следует превращать весь мир в огромное количество независимых флагов:

```text
door_open = true
npc_angry = true
quest_done = true
secret_found = true
faction_hostile = true
...
```

Такой подход быстро становится неуправляемым.

Вместо этого состояние должно быть связано с сущностями мира.

Например:

```text
LOCATION
    owner
    access_level
    security
    population
    infrastructure_state
```

```text
NPC
    location
    status
    faction
    relationships
    inventory
    goals
```

```text
FACTION
    territories
    resources
    relationships
    internal_state
```

```text
PLAYER
    location
    health
    knowledge
    inventory
    relationships
    reputation
    status
```

---

# 5. Сущности, имеющие состояние

Состояние может существовать у разных типов объектов.

Минимальные категории:

```text
WORLD
REGION
LOCATION
ROUTE
NPC
PLAYER
FACTION
ORGANIZATION
SETTLEMENT
ITEM
RESOURCE
DOCUMENT
INFORMATION
RELATIONSHIP
INVESTIGATION
EVENT
ENVIRONMENT
ECONOMY
ACCESS
```

Не каждая сущность обязана иметь одинаковую структуру.

# 6. Уровни состояния

Для удобства состояние делится на уровни.

## 6.1 GLOBAL STATE

Состояние всего мира.

Примеры:

```text
current_world_day
global_alert_level
global_weather_state
major_conflict_state
communication_network_state
known_exit_state
```

Глобальные изменения должны быть редкими.

---

## 6.2 REGIONAL STATE

Состояние региона.

Например:

```text
region_03.population
region_03.security
region_03.economy
region_03.infrastructure
region_03.weather
region_03.faction_control
```

---

## 6.3 LOCATION STATE

Состояние конкретного места.

Например:

```text
laboratory_07

owner = faction_A
security = HIGH
power = ON
access = RESTRICTED
research_status = ACTIVE
```

---

## 6.4 NPC STATE

Текущее состояние NPC.

Например:

```text
npc_104

location = settlement_02
status = ACTIVE
faction = faction_A
trust[player_17] = 42
current_goal = FIND_MISSING_RESEARCHER
```

---

## 6.5 PLAYER STATE

Состояние персонажа игрока.

Например:

```text
player_17

location = laboratory_07
status = ACTIVE
health = ...
inventory = ...
knowledge = ...
reputation = ...
relationships = ...
```

---

## 6.6 FACTION STATE

Например:

```text
faction_A

territory = ...
resources = ...
members = ...
security = ...
relations = ...
internal_conflict = ...
```

---

# 7. Shared State и Personal State

Это особенно важно для WORLD//ERROR.

Не всё состояние является общим для всех.

Есть:

### SHARED WORLD STATE

Общее состояние мира.

Например:

```text
здание уничтожено
NPC умер
мост разрушен
фракция захватила территорию
радиостанция отключена
```

Если мост разрушен, он разрушен для всех.

---

### PERSONAL STATE

Состояние конкретного персонажа.

Например:

```text
player_17 знает о туннеле
player_42 не знает о туннеле
```

Мир один.

Знание различается.

---

### PRIVATE DISCOVERY STATE

Некоторые вещи могут быть известны конкретному игроку, группе или фракции.

Например:

```text
secret_112

known_by:
    player_17
    player_31
    faction_B
```

При этом сам секрет существует независимо от того, кто о нём знает.

---

# 8. STATE OWNERSHIP

Каждое состояние должно иметь понятного владельца или источник истины.

Например:

```text
WORLD ENGINE
    ↓
WORLD STATE
```

Для предмета:

```text
ITEM STATE
```

Для NPC:

```text
NPC STATE
```

Для игрока:

```text
PLAYER STATE
```

Для знания:

```text
KNOWLEDGE STATE
```

Это важно потому, что разные системы не должны произвольно менять чужое состояние.

---

# 9. Единственный источник истины

Для каждого канонического состояния должен существовать **authoritative source**.

Например:

```text
warehouse.owner
```

не должен одновременно независимо храниться:

```text
warehouse.owner
faction_A.controlled_warehouses
player_map.warehouse_owner
npc_memory.warehouse_owner
```

как четыре независимых истины.

Иначе они рано или поздно разойдутся.

Правильнее:

```text
AUTHORITATIVE STATE
        ↓
derived views
        ↓
NPC knowledge
        ↓
player knowledge
        ↓
UI
```

---

# 10. Derived State

Некоторые значения не нужно хранить напрямую.

Их можно вычислять из других данных.

Например:

```text
faction_A_controls_location_17
```

может определяться через:

```text
location_17.owner = faction_A
```

А:

```text
route_available
```

может зависеть от:

```text
route.state
+
weather
+
security
+
access
+
active_events
```

Такие значения называются **DERIVED STATE**.

Важно отличать:

```text
CANONICAL STATE
```

от:

```text
DERIVED STATE
```

---

# 11. Почему нельзя хранить всё

Если хранить абсолютно каждое вычисляемое значение отдельно, появляется проблема:

```text
owner = faction_A

controlled_by_faction_A = true

faction_A_territory_count = 17

map_control_indicator = true

player_knows_control = true
```

После одного изменения необходимо обновить всё.

Если что-то забыть:

```text
WORLD STATE ≠ DERIVED DATA
```

Поэтому принцип:

> **Храним первичные факты. Вычисляем производные значения.**

---

# 12. State Transition

Состояние не должно изменяться произвольно.

Основной механизм:

```text
BEFORE
↓
EVENT
↓
VALIDATION
↓
STATE TRANSITION
↓
AFTER
```

Например:

```text
BEFORE

bridge.status = OPEN
```

Происходит событие:

```text
BRIDGE_COLLAPSE
```

Проверяются условия.

После:

```text
bridge.status = DESTROYED
```

Создаются последствия:

```text
route unavailable
travel time increased
settlement isolated
NPC schedule changed
new investigation clue created
```

---

# 13. State Transition должен быть атомарным

Если событие изменяет несколько связанных значений, они должны изменяться согласованно.

Например:

```text
warehouse.owner = faction_B
```

и одновременно:

```text
faction_A.territory -= warehouse
faction_B.territory += warehouse
```

Нельзя получить промежуточное состояние:

```text
warehouse.owner = faction_B

но

faction_A всё ещё считает склад своим
```

Для игрока такой момент не должен существовать как валидное состояние мира.

---

# 14. Invariants

Мир должен иметь правила, которые **никогда не должны нарушаться**.

Это называется invariant.

Примеры:

```text
один уникальный предмет не может одновременно находиться
у двух игроков
```

```text
мёртвый NPC не может одновременно иметь статус ACTIVE
```

```text
уничтоженное здание не может использоваться
как обычное действующее здание
```

```text
игрок не может находиться одновременно
в двух физических местах
```

```text
ресурс нельзя потратить дважды
```

```text
один и тот же уникальный EVENT
не должен применяться два раза
```

Invariants — одна из главных защит от разрушения долгоживущего мира.

---

# 15. Validation

Перед применением изменения система должна проверять его допустимость.

Например:

```text
PLAYER_TRAVEL
```

может проверять:

```text
существует ли маршрут
доступен ли маршрут
может ли персонаж пройти
не заблокирован ли маршрут
достаточно ли ресурсов
не произошло ли событие, запрещающее движение
```

Если условие не выполнено:

```text
STATE НЕ ИЗМЕНЯЕТСЯ
```

и создаётся соответствующий результат действия.

---

# 16. Event Log

Все значимые изменения должны иметь запись в журнале событий.

Например:

```text
EVENT #18422

type:
WAREHOUSE_CAPTURED

time:
DAY 81 / 14:32

location:
warehouse_07

initiator:
faction_B

before:
owner = faction_A

after:
owner = faction_B
```

Это позволяет:

* восстанавливать историю;
* искать ошибки;
* разбирать спорные ситуации;
* анализировать действия игроков;
* создавать расследования;
* откатывать ошибочные изменения;
* понимать происхождение состояния.

---

# 17. Snapshot + Event Log

Для долгоживущего мира одного event log недостаточно.

Если за пять лет произойдут миллионы событий, нельзя каждый раз восстанавливать весь мир с самого начала.

Поэтому используется комбинация:

```text
SNAPSHOT
+
EVENT LOG
```

Например:

```text
DAY 100
SNAPSHOT

↓
EVENT 10001
EVENT 10002
EVENT 10003
...
EVENT 10452

DAY 101
SNAPSHOT
```

При восстановлении:

```text
последний snapshot
+
последующие события
=
текущее состояние
```

---

# 18. Версии состояния

Мир должен иметь понятную версию состояния.

Например:

```text
WORLD_STATE_VERSION = 18452
```

Каждое значимое изменение увеличивает версию.

Это помогает:

* обнаруживать конфликты;
* синхронизировать системы;
* понимать порядок изменений;
* восстанавливать состояние;
* диагностировать ошибки.

---

# 19. Multiplayer и Race Conditions

В многопользовательской игре два игрока могут сделать что-то одновременно.

Например:

```text
Игрок A пытается взять предмет.

Игрок B пытается взять тот же предмет.
```

Оба видят:

```text
item.status = AVAILABLE
```

Но предмет может достаться только одному.

Поэтому операция должна выглядеть примерно так:

```text
READ CURRENT STATE
↓
VALIDATE
↓
LOCK / TRANSACTION
↓
APPLY CHANGE
↓
COMMIT
```

Второй игрок после этого получает уже изменённое состояние.

---

# 20. Не доверять клиенту

Telegram-интерфейс не является источником истины.

Игрок может отправить:

```text
"я открыл дверь"
```

Это только намерение.

Движок должен проверить:

```text
есть ли дверь
где находится игрок
есть ли доступ
есть ли ключ
не заблокирована ли дверь
не изменилось ли состояние
```

И только после проверки:

```text
ACTION
↓
EVENT
↓
STATE CHANGE
```

---

# 21. AI не является источником WORLD STATE

Это одно из главных архитектурных правил WORLD//ERROR.

AI может:

* разговаривать;
* формулировать;
* анализировать;
* создавать варианты текста;
* помогать NPC выражать мысли;
* составлять документы;
* объяснять доступные данные;
* адаптировать стиль общения.

Но AI не должен самостоятельно решать:

```text
кто умер
что произошло
существует ли объект
какая фракция владеет территорией
какова истинная история
изменился ли мировой канон
```

Правильная схема:

```text
WORLD ENGINE
      ↓
CANONICAL STATE
      ↓
AI получает разрешённый контекст
      ↓
AI формирует представление
      ↓
PLAYER
```

А не:

```text
AI
 ↓
придумал факт
 ↓
факт стал каноном
```

---

# 22. State Visibility

Не всё состояние доступно игроку.

Для каждого объекта может существовать:

```text
CANONICAL STATE
```

и различные представления:

```text
PLAYER A VIEW
PLAYER B VIEW
NPC VIEW
FACTION A VIEW
PUBLIC VIEW
```

Например:

```text
TRUTH:

NPC_17 работает на faction_B.
```

Игрок A:

```text
не знает
```

Игрок B:

```text
подозревает
```

NPC C:

```text
знает точно
```

Фракция A:

```text
имеет ложную информацию
```

Фракция B:

```text
знает правду
```

Состояние мира одно.

Представления разные.

---

# 23. State и Knowledge

Особенно важно:

```text
WORLD STATE
```

не должен смешиваться с:

```text
PLAYER KNOWLEDGE
```

Например:

```text
WORLD:

туннель существует.
```

Игрок:

```text
не знает о туннеле.
```

После обнаружения:

```text
WORLD:

туннель существует.

PLAYER KNOWLEDGE:

туннель существует.
```

Если игрок забудет или потеряет записи:

```text
WORLD:

туннель существует.

PLAYER KNOWLEDGE:

информация отсутствует / недоступна.
```

Мир не меняется только потому, что игрок забыл.

---

# 24. State Expiration

Некоторые состояния постоянны.

Например:

```text
building.destroyed
```

Некоторые временные:

```text
storm.active
```

Некоторые имеют срок действия:

```text
temporary_access
```

Поэтому состояние может иметь:

```text
START_TIME
END_TIME
DURATION
EXPIRATION_CONDITION
```

Но нельзя использовать таймеры для всего подряд.

Если событие мира отменяет состояние раньше срока, оно должно иметь приоритет.

---

# 25. Decay

Некоторые значения постепенно изменяются.

Например:

```text
reputation
trust
security_alert
food_stock
population
influence
market_price
```

Но изменение должно происходить по правилам мира.

Не:

```text
каждые 10 минут random -1
```

а:

```text
события
деятельность
потребление
производство
решения NPC
экономика
время
```

должны создавать изменение.

---

# 26. State History

Для значимых состояний нужно хранить историю.

Например:

```text
NPC_17
```

История:

```text
Day 1 — settlement_A
Day 4 — expedition camp
Day 12 — settlement_B
Day 15 — captured
Day 18 — escaped
```

Это позволяет миру помнить прошлое.

История также может стать:

* уликой;
* источником расследования;
* причиной отношений;
* частью биографии;
* основой для будущих событий.

---

# 27. State и Time

Состояние всегда существует во времени.

Поэтому важно различать:

```text
CURRENT STATE
```

и:

```text
STATE AT TIME T
```

Например:

```text
Сейчас:
bridge = DESTROYED
```

Но:

```text
Day 31:
bridge = OPEN
```

Игрок может найти старый документ и обнаружить, что мост существовал раньше.

Это связывает:

```text
STATE
+
HISTORY
+
INFORMATION
+
INVESTIGATION
```

---

# 28. State Migration

WORLD//ERROR должен существовать годами.

Значит, структура данных будет меняться.

Например, сначала:

```text
NPC:
name
location
status
```

Через год появляется:

```text
NPC:
name
location
status
goals
relationships
memory
faction_history
```

Нельзя просто сломать старые данные.

Нужны:

```text
SCHEMA VERSION
MIGRATION
VALIDATION
```

Например:

```text
STATE_SCHEMA = 3
```

При обновлении:

```text
VERSION 2
↓
MIGRATION
↓
VERSION 3
```

---

# 29. Recovery

Система должна переживать:

* перезапуск бота;
* падение сервера;
* ошибку базы;
* сбой Telegram API;
* частично выполненное действие;
* повторную доставку сообщения;
* сетевые ошибки;
* обновление кода.

После перезапуска:

```text
DATABASE
↓
SNAPSHOT
↓
EVENT LOG
↓
CURRENT WORLD STATE
```

Мир не должен начинаться заново.

---

# 30. Idempotency

Одно и то же событие не должно применяться дважды.

Например:

```text
EVENT_ID = 928381
```

Если система получила его повторно:

```text
EVENT_ID уже обработан
```

повторного изменения не происходит.

Это особенно важно для:

* Telegram;
* очередей;
* фоновых задач;
* сетевых операций;
* платежей;
* предметов;
* экономики;
* смерти персонажей;
* наград.

---

# 31. Ошибки состояния

Если система обнаружила невозможное состояние:

```text
dead NPC
+
active combat
```

или:

```text
item owned_by A
+
item owned_by B
```

это не должно молча исправляться случайным образом.

Нужно:

```text
VALIDATION ERROR
↓
LOG
↓
ALERT
↓
SAFE RECOVERY
```

Особенно для канонических данных.

Ошибка разработчика не должна превращаться в загадку для игроков.

---

# 32. Debug State

Для разработчика должна существовать возможность посмотреть:

```text
CURRENT STATE
```

и:

```text
WHY IS IT THIS WAY?
```

Например:

```text
warehouse.owner = faction_B

Причина:

EVENT #18422
WAREHOUSE_CAPTURED

initiator:
faction_B

time:
DAY 81

previous:
faction_A
```

Это крайне важно для игры с большим количеством скрытой логики.

---

# 33. Canonical State и Developer State

Не всё техническое состояние является частью канона.

Например:

```text
database_cache
queue_status
temporary_lock
AI_generation_job
```

не являются частью игрового мира.

Нужно разделять:

```text
GAME STATE
```

и:

```text
TECHNICAL STATE
```

Иначе технические детали могут случайно стать частью игровой логики.

# 34. Минимальная структура WORLD STATE

На концептуальном уровне:

```text
WORLD_STATE

world
├── global_state
├── regions
├── locations
├── routes
├── factions
├── organizations
├── npcs
├── players
├── items
├── resources
├── information
├── relationships
├── investigations
├── environment
├── economy
├── access
└── active_events
```

Но это логическая модель.

Конкретная структура базы данных будет определяться позже в:

```text
20_TECH_ARCHITECTURE.md
```

# 35. State Lifecycle

Общий жизненный цикл изменения:

```text
PLAYER / NPC / WORLD
        ↓
      ACTION
        ↓
    VALIDATION
        ↓
      EVENT
        ↓
   STATE TRANSITION
        ↓
   INVARIANT CHECK
        ↓
      COMMIT
        ↓
   DERIVED STATE
        ↓
 KNOWLEDGE / INFORMATION
        ↓
 PLAYER / NPC EXPERIENCE
```

# 36. Главный принцип архитектуры

Нельзя строить WORLD//ERROR как:

```text
команды Telegram
↓
изменение переменных
↓
сообщение игроку
```

Правильная модель:

```text
INTENT
↓
ACTION
↓
EVENT
↓
STATE TRANSITION
↓
WORLD STATE
↓
CONSEQUENCES
↓
INFORMATION
↓
PRESENTATION
```

Telegram — только один из способов взаимодействия с этим процессом.

---

# 37. Пример полного изменения мира

Игрок пытается открыть старую дверь.

### 1. Intent

```text
PLAYER:
открыть дверь
```

### 2. Validation

Движок проверяет:

```text
игрок находится у двери
дверь существует
дверь не уничтожена
есть необходимые условия
```

### 3. Event

```text
DOOR_OPENED
```

### 4. State

```text
door.status = OPEN
```

### 5. Consequences

За дверью обнаруживается помещение.

```text
location_17.discovery_state = DISCOVERED
```

### 6. Information

Игрок получает:

```text
PHOTO
DOCUMENT
OBSERVATION
```

### 7. Knowledge

```text
player_17 knows:
location_17 exists
```

### 8. World consequence

Позже:

```text
faction_B
```

узнаёт о проникновении через другого NPC.

Это создаёт:

```text
FACTION_EVENT
```

И спустя несколько дней:

```text
security_level ↑
```

Игрок мог вообще не увидеть связь между своим действием и последующим изменением.

# 38. Что должен уметь WORLD STATE

Система состояния должна позволять ответить:

### Что сейчас происходит?

```text
CURRENT STATE
```

### Почему это произошло?

```text
EVENT HISTORY
```

### Что изменится, если произойдёт X?

```text
EVENT / CONSEQUENCE MODEL
```

### Кто об этом знает?

```text
KNOWLEDGE STATE
```

### Что видит конкретный игрок?

```text
PLAYER VIEW
```

### Можно ли выполнить действие?

```text
VALIDATION
```

### Не сломался ли мир?

```text
INVARIANTS
```

### Что было раньше?

```text
HISTORY
```

# 39. Принцип минимально необходимого состояния

Не следует моделировать абсолютно всё.

Если значение:

* никогда не влияет на игровой процесс;
* не нужно для информации;
* не нужно для истории;
* не влияет на NPC;
* не влияет на последствия;

то его необязательно хранить как отдельное состояние.

WORLD//ERROR должен быть:

> **глубоким там, где глубина создаёт взаимодействие.**

Не:

> **сложным ради сложности.**

---

# 40. Основные правила WORLD STATE

1. **State — это текущее состояние мира.**
2. **Event — изменение состояния.**
3. **History — происхождение состояния.**
4. **Canonical state имеет единственный источник истины.**
5. **Производные значения желательно вычислять, а не дублировать.**
6. **Изменения проходят через валидируемые переходы.**
7. **Связанные изменения должны быть атомарными.**
8. **Нарушение invariant — ошибка системы.**
9. **Shared state отличается от personal state.**
10. **Knowledge не является частью объективной истины мира.**
11. **AI не является источником канонического состояния.**
12. **Telegram не является источником состояния.**
13. **Состояние должно переживать перезапуск системы.**
14. **Значимые изменения должны иметь историю.**
15. **Состояние должно быть диагностируемым.**
16. **Ошибки разработчика не становятся игровыми загадками.**
17. **Мир должен поддерживать миграции и развитие схемы.**
18. **Мир не должен моделироваться огромным набором несвязанных флагов.**
19. **Сложность должна появляться из взаимодействия систем.**
20. **WORLD STATE должен позволять понять не только “что сейчас”, но и “почему сейчас именно так”.**

# 41. Ключевая формула

```text
WORLD STATE
=
CURRENT TRUTH
+
RELATIONSHIPS
+
RESOURCES
+
KNOWLEDGE
+
ACCESS
+
ACTIVE CONDITIONS
```

Но:

```text
WORLD STATE ≠ HISTORY
WORLD STATE ≠ PLAYER VIEW
WORLD STATE ≠ AI OUTPUT
WORLD STATE ≠ TELEGRAM MESSAGE
```

# 42. Главный принцип WORLD//ERROR

> **Мир не должен помнить только то, что игрок увидел.**

Мир должен иметь собственное состояние.

Игрок видит лишь доступную ему проекцию этого состояния.

Поэтому:

```text
WORLD
  ↓
STATE
  ↓
EVENTS
  ↓
INFORMATION
  ↓
KNOWLEDGE
  ↓
INTERPRETATION
  ↓
PLAYER ACTION
  ↓
NEW EVENT
  ↓
NEW STATE
```

И цикл продолжается.

**WORLD//ERROR — это не база квестов.**

Это система, в которой:

> **мир существует → состояние меняется → информация распространяется → люди интерпретируют её → принимают решения → решения меняют мир.**
