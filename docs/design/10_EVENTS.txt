# WORLD//ERROR

## 10_EVENTS.md

### Система событий

---

# 1. Назначение

Событие — это изменение состояния мира, которое имеет причину, участников, последствия и историю.

События являются основным механизмом, через который мир развивается во времени.

В WORLD//ERROR:

```text
EVENT
→
CHANGE
→
CONSEQUENCE
→
NEW STATE
```

Событие может быть:

* вызвано игроком;
* вызвано NPC;
* вызвано фракцией;
* вызвано другим событием;
* вызвано временем;
* вызвано состоянием мира;
* случайным в рамках заданных правил;
* запланированным;
* скрытым от игроков.

---

# 2. Событие ≠ сообщение

Важно разделять:

```text
EVENT
```

и

```text
NOTIFICATION
```

Например:

> «В городе произошёл пожар».

Это может быть сообщение.

Но само событие:

```text
FIRE_EVENT
LOCATION:
город

CAUSE:
короткое замыкание

DAMAGE:
склад уничтожен

CONSEQUENCES:
дефицит ресурсов
```

Сначала происходит событие.

Потом мир и интерфейс могут сообщить о нём игрокам.

---

# 3. Событие ≠ квест

Квест обычно предполагает:

```text
GOAL
→
TASKS
→
REWARD
```

Событие может не иметь:

* цели для игрока;
* награды;
* маркера;
* объяснения;
* участия игрока.

Например:

```text
NPC умирает.
```

Это может быть полноценным мировым событием, даже если игрок никогда не узнает о нём.

---

# 4. Мир должен уметь существовать без игроков

События могут происходить независимо от игроков.

Например:

```text
FACTION_A
↓
принимает решение

↓
FACTION_A
начинает строительство

↓
возникает дефицит материалов

↓
FACTION_B
повышает цены

↓
возникает конфликт
```

Игрок может узнать об этом спустя неделю.

Или не узнать вообще.

---

# 5. Событие имеет причину

Желательно, чтобы значимые события имели причинную связь.

Минимальная модель:

```text
CAUSE
→
EVENT
→
CONSEQUENCE
```

Например:

```text
ресурсов мало
→
цены растут
→
начинаются конфликты
```

Причина может быть:

* известной;
* скрытой;
* ошибочно интерпретированной;
* неизвестной.

---

# 6. Событие может иметь несколько причин

Например:

```text
FIRE_EVENT

CAUSES:
- неисправность
- сухая погода
- отсутствие пожарных
- заблокированная дорога
```

Это позволяет строить более сложные цепочки.

---

# 7. Событие может иметь несколько последствий

Например:

```text
FIRE
├── уничтожает здание
├── убивает NPC
├── создаёт дефицит
├── меняет цены
├── вызывает расследование
├── ухудшает отношения фракций
└── создаёт новые улики
```

Одно событие может воздействовать на несколько систем.

---

# 8. Масштаб события

События делятся по масштабу.

```text
LEVEL 0 — PERSONAL
LEVEL 1 — LOCAL
LEVEL 2 — REGIONAL
LEVEL 3 — GLOBAL
LEVEL 4 — CANONICAL
```

### LEVEL 0 — PERSONAL

Затрагивает одного персонажа или небольшой круг.

Пример:

> NPC обиделся на игрока.

### LEVEL 1 — LOCAL

Затрагивает место или небольшое сообщество.

Пример:

> закрытие магазина.

### LEVEL 2 — REGIONAL

Затрагивает несколько мест.

Пример:

> блокада региона.

### LEVEL 3 — GLOBAL

Затрагивает значительную часть мира.

Пример:

> крупный политический кризис.

### LEVEL 4 — CANONICAL

Крупное историческое событие, изменяющее долгосрочное состояние мира.

Основные категории:


# 10. События игроков

Игроки являются одним из источников событий.

Например:

```text
PLAYER_ACTION
→
EVENT
```

Игрок:

* открывает дверь;
* продаёт ресурс;
* раскрывает секрет;
* убивает NPC;
* создаёт организацию;
* публикует документ;
* начинает конфликт;
* исследует территорию.

Действие становится событием только тогда, когда оно изменяет состояние мира.

---

# 11. Действие ≠ событие

Например:

> Игрок нажал кнопку «поговорить».

Это действие.

Если после разговора NPC:

> передал информацию,

это изменение состояния.

Можно зафиксировать:

```text
ACTION:
TALK

EVENT:
INFORMATION_TRANSFER

CONSEQUENCE:
PLAYER_GAINED_KNOWLEDGE
```

---

# 12. Скрытые события

Некоторые события не должны быть сразу видны игроку.

Например:

```text
FACTION_A
тайно отправляет агента.
```

Событие существует.

Игрок может узнать о нём позже:

* через свидетельство;
* документ;
* наблюдение;
* последствия;
* слух.

---

# 13. Видимость события

Событие может иметь:

```text
PUBLIC
LOCAL
PRIVATE
SECRET
HIDDEN
UNKNOWN
```

Важно:

> видимость события ≠ знание игрока о событии.

Событие может быть публичным, но конкретный игрок может его пропустить.

---

# 14. Источник события

У события должен быть инициатор или источник, если он существует.

Например:

```text
INITIATOR:
PLAYER_42
```

или:

```text
INITIATOR:
FACTION_7
```

или:

```text
INITIATOR:
WORLD_PROCESS
```

или:

```text
INITIATOR:
UNKNOWN
```

---

# 15. Участники события

Событие может иметь:

```text
ACTORS
VICTIMS
WITNESSES
TARGETS
BENEFICIARIES
AFFECTED_ENTITIES
```

Например:

```text
EVENT:
ограбление

ACTOR:
NPC_A

VICTIM:
NPC_B

WITNESS:
PLAYER_C

BENEFICIARY:
FACTION_D
```

---

# 16. События могут быть цепочками

Один из важнейших принципов:

```text
EVENT_A
↓
EVENT_B
↓
EVENT_C
↓
EVENT_D
```

Например:

```text
игрок публикует документ
↓
фракция узнаёт секрет
↓
фракция меняет стратегию
↓
возникает конфликт
↓
закрывается регион
↓
игроки теряют доступ
↓
возникает новое расследование
```

---

# 17. События могут иметь задержку

Последствие не обязано происходить сразу.

Например:

```text
PLAYER_ACTION
↓
EVENT_A

через 3 дня

EVENT_B
```

Это позволяет создавать долгосрочные последствия.

Игрок может даже не помнить первоначальное действие.

---

# 18. Отложенные события

Система может хранить:

```text
TRIGGER
EXECUTION_TIME
CONDITIONS
SOURCE
EXPECTED_EFFECT
```

Пример:

```text
TRIGGER:
если фракция узнает координаты

DELAY:
2 дня

EVENT:
экспедиция фракции
```

---

# 19. Условные события

Некоторые события происходят только при определённых условиях.

Например:

```text
IF:
ресурс найден
AND
фракция знает координаты
AND
дорога доступна

THEN:
фракция отправляет экспедицию
```

Это позволяет строить динамические цепочки.

---

# 20. Несколько возможных исходов

Событие не всегда должно иметь один фиксированный результат.

Например:

```text
FACTION_EXPEDITION

IF:
путь свободен
→ успех

IF:
путь заблокирован
→ задержка

IF:
встреча с другой фракцией
→ переговоры

IF:
атака
→ конфликт

IF:
ресурс исчез
→ расследование
```

Мир реагирует на текущее состояние.

---

# 21. Событие может отмениться

Если условия больше не выполняются:

```text
SCHEDULED EVENT
→ CANCELLED
```

Например:

Фракция планировала захватить территорию.

Но:

* территория уже занята;
* ресурс исчез;
* фракция потеряла людей;
* началась другая война.

План больше не выполняется.

---

# 22. Событие может измениться

Запланированное событие может трансформироваться.

Например:

```text
EXPEDITION
↓
AMBUSH
↓
RESCUE OPERATION
```

Это не обязательно три независимых квеста.

Это одна развивающаяся цепочка.

---

# 23. События и состояние мира

Событие не должно просто записываться в журнал.

Оно изменяет состояние.

Например:

```text
EVENT:
мост разрушен

WORLD STATE:
bridge.status = DESTROYED
```

После этого:

```text
ROUTE:
UNAVAILABLE
```

И:

```text
TRANSPORT:
затруднён
```

И:

```text
TRADE:
замедлен
```

---

# 24. Событие может создавать объекты

Например:

```text
FIRE
→
RUINS
```

или:

```text
CONSTRUCTION
→
NEW_BUILDING
```

или:

```text
DEATH
→
BODY
→
EVIDENCE
```

или:

```text
DISCOVERY
→
NEW_LOCATION
```

---

# 25. Событие может уничтожать объекты

Например:

```text
EXPLOSION
→
BUILDING_DESTROYED
```

или:

```text
FLOOD
→
ROAD_DESTROYED
```

или:

```text
FIRE
→
DOCUMENT_DESTROYED
```

Это должно отражаться в состоянии мира.

---

# 26. Событие может изменять отношения

Например:

```text
PLAYER_A
betrays
FACTION_B
```

создаёт:

```text
RELATION:
TRUST ↓
REPUTATION ↓
HOSTILITY ↑
```

Событие может менять отношения между:

* игроками;
* NPC;
* игроком и NPC;
* фракциями;
* организациями.

---

# 27. Событие может менять знания

Например:

```text
EVENT:
NPC_A сообщает игроку секрет.
```

Последствие:

```text
PLAYER_KNOWLEDGE += INFORMATION_X
```

Или:

```text
EVENT:
документ уничтожен.

CONSEQUENCE:
доступ к информации уменьшается.
```

---

# 28. Событие может создавать новые улики

Например:

```text
NPC убит.
```

Создаются:

```text
BODY
BLOOD
LOCATION_STATE
WITNESS_TESTIMONY
FORENSIC_EVIDENCE
```

Это создаёт основу для нового расследования.

---

# 29. Событие может изменять значение старых улик

Например:

```text
EVENT:
обнаружена новая дата.
```

После этого старая фотография получает новую интерпретацию.

Поэтому события могут влиять не только на будущую информацию, но и на понимание уже существующей.

---

# 30. События и время

Событие должно иметь временную модель.

Минимально:

```text
CREATED_AT
STARTED_AT
ENDED_AT
DISCOVERED_AT
```

Некоторые события происходят мгновенно.

Другие продолжаются:

```text
WAR
STORM
SIEGE
INVESTIGATION
CONSTRUCTION
DISEASE_OUTBREAK
```

---

# 31. Состояния события

```text
PLANNED
TRIGGERED
ACTIVE
PAUSED
COMPLETED
FAILED
CANCELLED
INTERRUPTED
UNKNOWN
```

---

# 32. Повторяющиеся события

Некоторые события могут повторяться.

Например:

```text
MARKET_DAY
PATROL
TRAIN_ARRIVAL
WEATHER_EVENT
```

Но повторяющиеся события не должны быть просто бесконечным циклом.

Они могут зависеть от состояния мира.

---

# 33. Периодические события

Например:

```text
каждые 7 дней:
рынок

если безопасность низкая:
рынок может быть отменён
```

Таким образом расписание связано с миром.

---

# 34. Случайные события

Случайность допустима, но должна иметь границы.

Плохо:

```text
рандом:
NPC умер
```

Хорошо:

```text
NPC находится в опасной зоне
+
идёт вооружённый конфликт
+
NPC отправился в экспедицию
=
существует вероятность смерти
```

Случайность должна работать внутри модели мира.

---

# 35. События должны быть объяснимыми

Даже если игрок не знает причину события, движок должен её знать.

Например:

```text
PLAYER SEES:
NPC исчез.
```

Внутри системы:

```text
CAUSE:
FACTION_A captured NPC.
```

Игрок может обнаружить это позже.

---

# 36. События без известной причины

Допустимы ситуации:

```text
CAUSE:
UNKNOWN
```

Но это должно быть осознанным состоянием.

Например:

* неизвестное исчезновение;
* аномальное явление;
* потерянная историческая запись;
* неизвестный источник сигнала.

---

# 37. Канонические события

Некоторые события должны иметь особый статус.

Например:

```text
CANONICAL
```

Они являются частью основной истории мира.

Но даже каноническое событие может иметь:

* неизвестную причину;
* разные свидетельства;
* неполные данные;
* ошибочные официальные версии.

---

# 38. Локальные события

Большинство событий не должны быть мировыми.

Например:

```text
NPC_A поругался с NPC_B.
```

Это может иметь значение только для одного поселения.

Важно сохранять масштаб.

Если каждое действие игрока меняет весь мир, мир перестанет ощущаться большим.

---

# 39. Масштабирование последствий

Используется принцип:

```text
SMALL ACTION
→
SMALL CONSEQUENCE
```

но иногда:

```text
SMALL ACTION
→
HIDDEN CHAIN
→
LARGE CONSEQUENCE
```

Второй вариант должен быть редким и значимым.

---

# 40. Событие и игрок

Игрок может быть:

```text
CAUSE
PARTICIPANT
WITNESS
VICTIM
BENEFICIARY
TARGET
INVESTIGATOR
UNAWARE
```

Один игрок может одновременно занимать несколько ролей.

---

# 41. Событие и несколько игроков

Событие может затрагивать многих игроков.

Например:

```text
PLAYER_A
открывает шахту

PLAYER_B
торгует ресурсами

PLAYER_C
пытается захватить шахту

PLAYER_D
публикует координаты
```

Все они становятся частью одной цепочки событий.

---

# 42. События могут конкурировать

Одновременно могут происходить:

```text
EVENT_A:
фракция готовит захват

EVENT_B:
игроки готовят оборону

EVENT_C:
третья фракция предлагает переговоры
```

Результат зависит от того, какое событие произойдёт раньше и какие условия изменятся.

---

# 43. События могут прерываться

Например:

```text
CONSTRUCTION
```

может быть прервано:

* нападением;
* нехваткой ресурсов;
* погодой;
* решением фракции;
* смертью ответственного NPC.

После этого событие может:

* продолжиться;
* завершиться;
* превратиться в другое;
* быть отменено.

---

# 44. События могут иметь скрытые последствия

Например:

```text
PLAYER STEALS DOCUMENT
```

Немедленно:

```text
PLAYER получает документ.
```

Через неделю:

```text
FACTION обнаруживает пропажу.
```

Ещё позже:

```text
FACTION начинает искать виновного.
```

Ещё позже:

```text
FACTION проверяет игроков.
```

Игрок может не связать эти события.

---

# 45. События и причинные графы

Внутренне мир можно представлять как граф:

```text
EVENT_A
 ├──→ EVENT_B
 │      └──→ EVENT_D
 │
 └──→ EVENT_C
        └──→ EVENT_D
```

То есть одно событие может иметь несколько ветвей.

---

# 46. Событие может иметь альтернативные последствия

Например:

```text
DOCUMENT_STOLEN
```

может привести к:

```text
A:
игрок продал документ

→ фракция получает его обратно

B:
игрок уничтожил документ

→ начинается расследование

C:
игрок опубликовал документ

→ возникает политический кризис

D:
игрок спрятал документ

→ событие остаётся скрытым
```

---

# 47. События не обязаны быть уникальными

Мир может иметь множество похожих событий:

```text
THEFT
THEFT
THEFT
```

Но конкретный контекст делает их разными.

Событие определяется не только типом, но и:

* участниками;
* местом;
* временем;
* причиной;
* состоянием мира;
* последствиями.

---

# 48. История события

Каждое важное событие должно сохранять:

```text
EVENT_ID
TYPE
SCALE
CREATED_AT
STARTED_AT
ENDED_AT
INITIATOR
ACTORS
LOCATION
CAUSES
CONSEQUENCES
PARENT_EVENTS
CHILD_EVENTS
VISIBILITY
STATUS
```

Дополнительно:

```text
DISCOVERED_BY
RELATED_INFORMATION
RELATED_EVIDENCE
RELATED_FACTIONS
RELATED_NPCS
```

---

# 49. Журнал событий

Движок должен иметь внутренний журнал.

Он необходим для:

* отладки;
* восстановления состояния;
* расследования багов;
* анализа цепочек;
* проверки причин;
* тестирования мира.

Например:

```text
EVENT_1042
created: 2026-04-17
cause: EVENT_1031
actor: NPC_77
location: LOCATION_12
consequence: ROUTE_4_BLOCKED
```

---

# 50. Игрок не должен видеть журнал движка

Внутренний журнал:

```text
DEBUG / CANON
```

отличается от:

```text
PLAYER HISTORY
```

Игрок может видеть только доступные ему сведения.

---

# 51. События и сообщения Telegram

Telegram является интерфейсом, а не самим миром.

Событие может вызвать:

```text
Telegram message
```

Но сообщение не является событием.

Например:

```text
WORLD EVENT:
NPC умер.

↓

PRIVATE MESSAGE:
«Вы получили известие о смерти NPC».
```

Другой игрок может:

* не получить сообщение;
* узнать через NPC;
* увидеть тело;
* услышать слух;
* вообще никогда не узнать.

---

# 52. События могут создавать контент

Событие может породить:

* сообщение;
* документ;
* слух;
* новость;
* NPC-диалог;
* изменение карты;
* новую улику;
* изменение экономики;
* изменение отношений.

Но контент является представлением события.

---

# 53. AI и события

AI может помогать:

* описывать событие;
* генерировать диалоги;
* формулировать сообщения;
* создавать варианты документов;
* адаптировать подачу.

Но AI не должен самостоятельно решать:

> произошло ли событие на самом деле.

Движок создаёт событие.

AI объясняет или представляет его.

---

# 54. События и канон

Каноническое событие должно быть создано или подтверждено движком/авторской системой.

AI-generated content не становится каноном автоматически.

---


---

# 56. Событийный движок

В перспективе система должна работать примерно так:

```text
WORLD STATE
↓
CHECK CONDITIONS
↓
TRIGGER EVENT
↓
RESOLVE EVENT
↓
APPLY CONSEQUENCES
↓
UPDATE WORLD STATE
↓
GENERATE INFORMATION
↓
UPDATE KNOWLEDGE
↓
SCHEDULE FUTURE EVENTS
```

---

# 57. Пример полного цикла

Допустим, игрок украл документ.

```text
ACTION:
PLAYER steals DOCUMENT_A
```

Движок создаёт:

```text
EVENT_100:
DOCUMENT_STOLEN
```

Изменения:

```text
DOCUMENT_A.owner = PLAYER
ARCHIVE_A.document_missing = true
```

Затем:

```text
EVENT_101:
ARCHIVE_DISCOVERS_LOSS
```

Через несколько дней:

```text
EVENT_102:
FACTION_INVESTIGATION
```

Затем:

```text
EVENT_103:
NPC questioned
```

И затем:

```text
EVENT_104:
FACTION suspects PLAYER
```

Игрок может вообще не знать о событиях 101–104.

Но мир уже изменился.

---

# 58. Событие может создавать расследование

Особенно важный цикл:

```text
EVENT
↓
INFORMATION
↓
EVIDENCE
↓
PLAYER DISCOVERS
↓
INVESTIGATION
↓
ACTION
↓
NEW EVENT
```

Таким образом расследования естественно возникают из симуляции.

---

# 59. Событие может создавать другое расследование

Например:

```text
NPC исчез.
```

Игрок расследует исчезновение.

Позже выясняется:

```text
NPC был похищен.
```

Это создаёт новый вопрос:

> Кто похитил NPC?

После этого:

> Зачем?

После этого:

> Кто финансировал похищение?

И так далее.

---

# 60. Событие может быть незамеченным

Не каждое событие обязано становиться контентом для игроков.

Например:

```text
NPC_A умер.
```

Если никто не был рядом и никто не знает:

```text
WORLD:
NPC_A = DEAD

PLAYER KNOWLEDGE:
ничего
```

Через неделю игрок может обнаружить последствия.

---

# 61. Мир не обязан объяснять всё

Если игрок не обнаружил событие, игра не должна обязательно рассказывать ему:

> «Три дня назад здесь произошло X».

Игрок должен иметь возможность пропустить информацию.

Это поддерживает ощущение независимого мира.

---

# 62. События должны иметь цену

Большие события требуют ресурсов.

Например:

```text
FACTION WAR
```

требует:

* людей;
* оружия;
* транспорта;
* снабжения;
* информации;
* времени;
* территории.

Фракция не должна объявлять войну только потому, что сюжет этого требует.

---

# 63. Ограничения событий

Перед выполнением события движок должен учитывать:

```text
RESOURCES
TIME
LOCATION
ACTORS
KNOWLEDGE
RELATIONSHIPS
ACCESS
WORLD_STATE
RISK
```

Это превращает события в часть симуляции.

---

# 64. Приоритет событий

Не все возможные события должны выполняться одновременно.

Система может учитывать:

```text
URGENCY
IMPORTANCE
RISK
RESOURCE_COST
FACTION_PRIORITY
WORLD_PRIORITY
PLAYER_IMPACT
```

Это особенно важно при большом количестве NPC и фракций.

---

# 65. События должны быть масштабируемыми

Мир может содержать:

```text
тысячи мелких событий
сотни средних событий
десятки крупных событий
единицы мировых событий
```

Но игрок не обязан видеть всё.

---

# 66. Главное ограничение

Нельзя строить мир как бесконечную очередь скриптов:

```text
если X → Y
если Y → Z
если Z → Q
```

Такая система быстро станет неуправляемой.

Предпочтительно:

```text
STATE
+
RULES
+
EVENTS
+
CONSEQUENCES
```

То есть события должны изменять состояние мира, а новое состояние влияет на следующие события.

---

# 67. Событие как атомарное изменение

Для технической архитектуры полезно стремиться к тому, чтобы событие можно было представить как:

```text
BEFORE
→
EVENT
→
AFTER
```

Например:

```text
BEFORE:
bridge = OPEN

EVENT:
BRIDGE_DESTROYED

AFTER:
bridge = DESTROYED
```

Это облегчает:

* сохранение;
* восстановление;
* тестирование;
* откат;
* анализ;
* отладку.

---

# 68. Идемпотентность

Движок должен избегать ситуации, когда одно событие случайно применяется дважды.

Например:

```text
EVENT_501
```

не должен дважды:

```text
списать ресурс
убить NPC
изменить отношения
```

У каждого события должен быть уникальный ID и статус обработки.

---

# 69. Ошибки событий

Если событие не может быть выполнено:

```text
EVENT_FAILED
```

Но причина должна сохраняться.

Например:

```text
FAILED:
required NPC unavailable
```

Это необходимо для отладки и анализа мира.

---

# 70. Главный принцип

> **Мир не состоит из квестов. Мир состоит из состояний и изменений этих состояний.**

События — механизм, через который эти изменения происходят.

---

# 71. Основная формула WORLD//ERROR

```text
WORLD STATE
↓
CONDITIONS
↓
EVENT
↓
CONSEQUENCES
↓
NEW WORLD STATE
↓
INFORMATION
↓
PLAYER KNOWLEDGE
↓
PLAYER ACTION
↓
NEW EVENT
```

Именно этот цикл должен стать фундаментом всей симуляции WORLD//ERROR.

---

# 72. Итог

Система событий должна позволять создать мир, в котором:

* игроки не являются центром каждой ситуации;
* NPC действуют самостоятельно;
* фракции принимают решения;
* события происходят без игроков;
* действия имеют последствия;
* последствия могут быть отложенными;
* события могут создавать расследования;
* расследования могут создавать новые события;
* маленькие действия иногда запускают большие цепочки;
* мир сохраняет историю произошедшего;
* игрок видит только доступную ему часть происходящего.

> **Событие — это не кусок сюжета.
> Событие — это изменение мира.**
