# WORLD//ERROR — Roadmap

## 1. Назначение

Roadmap определяет последовательность создания WORLD//ERROR от пустого репозитория до первой устойчивой версии игры.

Главный принцип:

> Не строить следующий слой, пока предыдущий не доказал, что работает.

Roadmap должен минимизировать:

* технический долг;
* преждевременную сложность;
* зависимость от AI;
* переписывание WORLD ENGINE;
* чрезмерное производство контента;
* масштабирование слишком рано;
* создание систем, которые не используются игроками.

# 3. PHASE 0 — ПОДГОТОВКА

## Цель

Подготовить проект до написания сложной игровой логики.

### Сделать

* Git repository;
* базовую структуру проекта;
* DEV environment;
* STAGING environment;
* базовую database;
* migrations;
* configuration;
* logging;
* testing framework;
* environment variables;
* CI;
* basic deployment.

### Не делать

* AI;
* сложный Telegram UI;
* procedural generation;
* экономику;
* тысячи объектов.

# 23. CHECKPOINT 5

# 51. НАЗНАЧЕНИЕ ПЕРВОГО PLAYTEST

# 52. PLAYTEST QUESTIONS

После игры спросить:

1. Что, по-твоему, произошло?
2. Что ты считаешь фактом?
3. Что ты считаешь слухом?
4. Что тебя удивило?
5. Что изменилось после твоих действий?
6. Что происходило без тебя?
7. Хотелось ли тебе вернуться?
8. Что ты ожидал от NPC?
9. Что было непонятно из-за дизайна?
10. Что было непонятно специально?

Последний вопрос особенно важен.

# 70. НОВЫЙ ИГРОК В СТАРЫЙ WORLD INSTANCE

Очень важный тест.

```text id="q5m8r3"

```

а мир существует:

```text id="m9q3v7"

```

Новый игрок должен иметь:

* точку входа;
* доступные знания;
* возможность влиять;

> «Все интересное уже закончилось.»

# 71. DEATH И LONG-TERM ENTRY

Смерть должна не разрушать долгосрочную игру.

Новый персонаж может:

* исследовать старую историю;
* найти след старого персонажа;
* вступить в изменившиеся организации;
* воспользоваться оставшимися объектами;
* создать новую историю.

---

# 72. PHASE 42 — WORLD EXPANSION

Только когда начальный регион начинает реально использоваться.

Добавлять:

```text id="r4m8q2"
NEW REGION
↓
NEW LOCATIONS
↓
NEW FACTIONS
↓
NEW ECONOMY
↓
NEW HISTORY
```

Не расширять карту просто ради размера.

---

# 73. РЕГИОН ДОЛЖЕН ИМЕТЬ ПРИЧИНУ ПОЯВИТЬСЯ

Новая территория может стать доступной через:

* исследование;
* изменение границы;
* транспорт;
* политическое событие;
* разрушение барьера;
* получение информации;
* технологию;
* экспедицию.

Расширение должно быть частью мира.

---

# 74. PHASE 43 — MULTI-WORLD FEATURES

По умолчанию WORLD INSTANCE остаются изолированными.

Только после зрелости игры можно рассматривать:

* глобальные immutable resources;
* shared ARG;
* community canon;
* cross-instance events;
* tournaments;
* external world layers.

Это должно быть отдельным дизайном.

---

# 75. НЕ ДОБАВЛЯТЬ CROSS-INSTANCE GAMEPLAY СЛУЧАЙНО

Если два мира взаимодействуют, это должно быть явно определено.

Например:

```text id="n7m2q4"
WORLD A
      ↓
GLOBAL EVENT
      ↓
WORLD B
```

Но такое событие должно иметь формальный механизм.

---

# 76. RELEASE CANDIDATE

Перед первым публичным запуском:

### Проверить

* persistence;
* backups;
* recovery;
* security;
* permissions;
* AI failures;
* Telegram failures;
* database failures;
* race conditions;
* duplicated events;
* item duplication;
* money duplication;
* hidden information leaks;
* cross-instance leaks.

---

# 77. PUBLIC RELEASE

Публичный запуск не должен означать:

> «Теперь игра закончена.»

Это означает:

> «Базовая система доказана достаточно хорошо, чтобы начать долгую эксплуатацию.»

---

# 78. POST-RELEASE

FIX

TEST

OBSERVE

Не:

ADD FEATURE

---

# 79. METRICS ПОСЛЕ ЗАПУСКА

Смотреть:

### Gameplay

* daily active characters;
* sessions;
* actions;
* investigations started;
* investigations completed;
* discoveries;
* deaths;
* faction joins;
* trades.

### World

* events;
* world changes;
* NPC actions;
* scheduled events;
* unresolved investigations.

### Technical

* latency;
* errors;
* event failures;
* queue;
* DB load;
* AI failures.

---

# 80. НЕ ИСПОЛЬЗОВАТЬ МЕТРИКИ КАК ЦЕЛЬ

Например:

> «Нужно, чтобы игроки сделали 100 действий в день.»

Это может привести к grind.

Лучше измерять:

> какие действия действительно создают meaningful state changes?

---

# 81. FEATURE GATE

Перед добавлением новой системы задать пять вопросов:

1. Какую проблему она решает?
2. Какую существующую систему она использует?
3. Какие новые последствия она создаёт?
4. Можно ли обойтись существующими механизмами?
5. Как мы поймём, что она действительно улучшила игру?

Если ответов нет — система откладывается.

---

# 82. СИСТЕМА НЕ ДОБАВЛЯЕТСЯ РАДИ СИСТЕМЫ

Плохая причина:

> «Нам нужна система крафта, потому что в больших играх есть крафт.»

Хорошая причина:

> «Игрокам нужен способ превращать найденные ресурсы в инструменты, которые открывают новые способы взаимодействия с миром.»

---

# 83. CONTENT GATE

Перед добавлением нового контента спросить:

> Как этот контент связан хотя бы с двумя существующими системами?

Например:

```text id="q8m3v1"
NEW LOCATION
↓
NPC
↓
CLUE
↓
FACTION
↓
ECONOMY
```

Контент, который существует полностью изолированно, подозрителен.

---

# 84. SYSTEM DENSITY

Хороший контент должен использовать несколько систем.

Например:

```text id="m7q2n8"
ABANDONED FACILITY
│
├── NPC
├── DOCUMENT
├── RESOURCE
├── FACTION INTEREST
├── INVESTIGATION
├── ECONOMY
└── HIDDEN AREA
```

Одна локация может создавать много gameplay.

---

# 85. ROADMAP НЕ ЛИНЕЙНЫЙ НАВСЕГДА

После первой альфы некоторые этапы будут повторяться:

# 86. ПРАВИЛО ПРОТОТИПА

Если систему можно проверить за несколько дней маленьким прототипом — сначала сделать прототип.

Не строить production architecture на основании предположения.

# 88. НЕ ПРОТОТИПИРОВАТЬ БЕСКОНЕЧНО

# 89. SYSTEM RETIREMENT

Система может быть удалена.

Если:

* никто не использует;
* она не создаёт интересных решений;
* создаёт слишком много сложности;
* дублирует другую систему.

Не нужно сохранять механику только потому, что на неё уже потрачено время.

# 106. КОНЕЧНАЯ ЦЕЛЬ

Не построить огромную игру сразу.

Построить систему, которая способна **становиться огромной без разрушения собственного фундамента**.

```text id="q8m4n7"
SMALL ENGINE
      ↓
SMALL WORLD
      ↓
REAL PLAYERS
      ↓
REAL CONSEQUENCES
      ↓
REAL HISTORY
      ↓
MORE SYSTEMS
      ↓
MORE WORLDS
      ↓
MORE HISTORY
      ↓
WORLD//ERROR
```

Именно так должен начинаться WORLD//ERROR.
