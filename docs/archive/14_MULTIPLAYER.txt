# WORLD//ERROR — 14_MULTIPLAYER.md

# Мультиплеер

## 1. Назначение документа

Этот документ определяет, как несколько игроков одновременно существуют в одном постоянном мире WORLD//ERROR.

Главный принцип:

> **Игроки не играют в отдельные копии мира. Они живут в одном мире, но имеют разные позиции, знания, отношения и возможности внутри него.**

---

# 2. Основная модель

WORLD//ERROR — это:

```text
ONE WORLD
+
MANY PLAYERS
+
DIFFERENT KNOWLEDGE
+
DIFFERENT ACTIONS
+
SHARED CONSEQUENCES
```

То есть:

```text
PLAYER A ─┐
PLAYER B ─┤
PLAYER C ─┼──→ SHARED WORLD
PLAYER D ─┤
PLAYER E ─┘
```

Все игроки воздействуют на одну систему состояния мира.

---

# 3. Один мир — не одинаковый опыт

Игроки не должны видеть одно и то же.

Например:

```text
PLAYER A:
знает о существовании тоннеля

PLAYER B:
знает, что в этом районе пропадают люди

PLAYER C:
имеет карту

PLAYER D:
думает, что тоннеля не существует
```

При этом:

```text
WORLD TRUTH
=
тоннель действительно существует.
```

Разница находится не в мире.

Разница находится в:

```text
KNOWLEDGE
ACCESS
RELATIONSHIPS
POSITION
REPUTATION
HISTORY
```

---

# 4. Shared World State

Следующие элементы в нормальном случае являются общими:

* география;
* физические объекты;
* состояние зданий;
* фракции;
* экономика;
* глобальные события;
* NPC;
* маршруты;
* погода;
* контроль территорий;
* разрушения;
* открытые игроками общественные объекты;
* история мира.

Если мост разрушен одним игроком:

```text
PLAYER A:
мост разрушен

PLAYER B:
мост тоже разрушен.
```

Не существует:

```text
PLAYER A WORLD
PLAYER B WORLD
```

---

# 5. Personal State

При этом некоторые данные принадлежат конкретному персонажу:

```text
inventory
knowledge
relationships
personal reputation
location
health
status
private documents
personal notes
private discoveries
```

Поэтому:

```text
WORLD STATE
≠
PLAYER STATE
```

---

# 6. Три уровня состояния

Полезно разделить:

### WORLD

Общее состояние мира.

### GROUP

Состояние группы, организации или объединения игроков.

### PLAYER

Состояние конкретного персонажа.

Например:

```text
WORLD:
мост разрушен

GROUP:
экспедиция контролирует склад

PLAYER:
у игрока есть ключ от склада
```

---

# 7. Multiplayer Authority

Для каждого изменения должен существовать источник авторитета.

Основной порядок:

```text
WORLD ENGINE
↓
RULES
↓
EVENT
↓
STATE CHANGE
```

Игрок не может сам объявить:

> «Я теперь владею этим городом».

Он может совершить действие:

```text
попытка захватить объект
```

Дальше движок определяет результат.

---

# 8. Нельзя доверять клиенту

Telegram-сообщение:

> «Я убил NPC.»

не является фактом.

Это только:

```text
PLAYER INTENT
```

Движок проверяет:

```text
может ли игрок?
где он находится?
есть ли оружие?
доступна ли цель?
происходит ли конфликт?
есть ли другие участники?
```

После этого:

```text
ACTION
→ VALIDATION
→ EVENT
→ STATE CHANGE
```

---

# 9. Player Intent

Полезно различать:

```text
INTENT
ACTION
EVENT
RESULT
```

Например:

```text
INTENT:
игрок хочет открыть дверь

ACTION:
использовать ключ

EVENT:
попытка открытия

RESULT:
дверь открыта
```

Или:

```text
INTENT:
игрок хочет открыть дверь

ACTION:
взломать

EVENT:
попытка взлома

RESULT:
неудача
```

---

# 10. Одновременные действия

В multiplayer два игрока могут действовать одновременно.

Например:

```text
PLAYER A:
берёт предмет

PLAYER B:
берёт тот же предмет
```

Система должна иметь определённый порядок разрешения.

Например:

```text
ACTION A
timestamp = 12:03:41.102

ACTION B
timestamp = 12:03:41.180
```

Если A успешно забрал предмет первым:

```text
ITEM
→ A
```

Для B:

```text
ITEM_NOT_AVAILABLE
```

---

# 11. Race Condition

Нельзя допускать:

```text
A checks item exists
B checks item exists

A takes item
B takes item

RESULT:
two copies
```

если предмет не допускает копирования.

Изменение состояния должно происходить атомарно.

---

# 12. Atomic Action

Критические действия должны выполняться как единая операция:

```text
CHECK
↓
VALIDATE
↓
CHANGE STATE
↓
CREATE EVENT
↓
COMMIT
```

Либо операция не происходит вообще.

---

# 13. Shared Object

Например, существует:

```text
OBJECT:
GENERATOR_001
```

Его состояние:

```text
LOCATION = WAREHOUSE
STATUS = ACTIVE
OWNER = SETTLEMENT_A
```

Игрок A чинит генератор.

Игрок B одновременно пытается его разобрать.

Движок должен определить последовательность:

```text
A → REPAIR
↓
STATE = ACTIVE

B → DISASSEMBLE
↓
VALIDATION
↓
allowed / denied
```

---

# 14. Concurrent Actions

Некоторые действия могут происходить одновременно.

Например:

```text
A разговаривает с NPC
B исследует здание
C охраняет вход
D торгует
```

Они не обязательно конфликтуют.

Поэтому concurrency должна быть:

```text
ALLOW
```

если действия независимы.

---

# 15. Conflict Resolution

Если действия конфликтуют:

```text
ACTION A
vs
ACTION B
```

движок использует:

1. временную последовательность;
2. состояние мира;
3. физическую возможность;
4. правила действия;
5. приоритет события;
6. результаты предыдущих действий.

Нельзя использовать:

> «кто написал красивее».

---

# 16. Multiplayer ≠ всем всё видно

В WORLD//ERROR необходимо разделять:

```text
WORLD EVENT
```

и:

```text
PLAYER VISIBILITY
```

Событие может произойти для всего мира.

Но информация о нём доступна только:

* свидетелям;
* участникам;
* NPC;
* фракции;
* игрокам с определённым доступом;
* тем, кто обнаружил последствия.

---

# 17. Visibility

У события могут быть уровни видимости:

```text
PUBLIC
LOCAL
PARTICIPANT
PRIVATE
SECRET
HIDDEN
UNKNOWN
```

Например:

```text
PLAYER A
совершил кражу ночью.
```

Мир знает:

```text
EVENT EXISTS
```

Но не обязательно знает:

```text
WHO DID IT
```

---

# 18. Information Asymmetry

Ассиметрия информации — одна из главных механик WORLD//ERROR.

Например:

```text
A knows X
B knows Y
C knows Z
```

Только вместе:

```text
X + Y + Z
```

позволяют предположить:

```text
HYPOTHESIS
```

---

# 19. Knowledge Sharing

Игрок может передавать информацию.

Например:

```text
A:
"Я нашёл координаты."
```

Это не означает автоматически:

```text
B.KNOWLEDGE += coordinates
```

Нужно событие передачи:

```text
A → COMMUNICATE → B
```

После этого B получает информацию.

---

# 20. Information Can Be Withheld

Игрок может:

* не рассказать;
* соврать;
* рассказать частично;
* передать поддельный документ;
* продать информацию;
* передать только координаты;
* скрыть источник.

Поэтому:

```text
PLAYER KNOWLEDGE
```

не является автоматически:

```text
PUBLIC KNOWLEDGE
```

---

# 21. Private Discovery

Некоторые открытия принадлежат только игроку до момента публикации.

Например:

```text
PLAYER A discovers:
SECRET_ROOM
```

Состояние:

```text
WORLD:
комната существует

PLAYER A:
знает

PLAYER B:
не знает
```

Если A сообщает B:

```text
B.KNOWLEDGE += SECRET_ROOM
```

---

# 22. Discovery Race

Два игрока могут независимо обнаружить одно и то же.

Например:

```text
A discovers object
```

а через минуту:

```text
B discovers object
```

Первое открытие может иметь:

```text
FIRST_DISCOVERY
```

Но это не должно навсегда давать игроку абсолютное право на объект.

Нужно различать:

```text
DISCOVERED
LOCATED
REACHED
CONTROLLED
OWNED
```

---

# 23. Discovery ≠ Ownership

Если игрок нашёл локацию:

```text
DISCOVERY
```

это не значит:

```text
OWNERSHIP
```

Если игрок нашёл ресурс:

```text
DISCOVERY
```

это не значит:

```text
RESOURCE_RIGHTS
```

Это особенно важно для multiplayer.

---

# 24. Group Formation

Игроки могут объединяться.

Минимальные уровни:

```text
TEMPORARY GROUP
PLAYER GROUP
COMMUNITY
ORGANIZATION
RECOGNIZED ORGANIZATION
CANONICAL FACTION
```

---

# 25. Temporary Group

Простейшее объединение:

```text
A + B + C
```

для одной операции.

Например:

> «Пойдём вместе исследовать туннель».

После операции группа может исчезнуть.

---

# 26. Persistent Group

Игроки могут создать постоянное объединение:

```text
GROUP_001
```

с:

* названием;
* участниками;
* правилами;
* целями;
* общими ресурсами;
* историей;
* репутацией.

---

# 27. Organization

Более крупное объединение получает:

```text
roles
permissions
treasury
assets
territory
diplomacy
membership
internal structure
```

Например:

```text
LEADER
OFFICER
MEMBER
RECRUIT
```

Но структура может быть любой.

---

# 28. Organization Is Not Automatically Faction

Игроки создали организацию:

```text
GROUP
```

Она не становится автоматически частью канона.

Может быть:

```text
COMMUNITY
```

или:

```text
UNRECOGNIZED ORGANIZATION
```

Позже:

```text
RECOGNIZED
```

и потенциально:

```text
CANONICAL FACTION
```

---

# 29. Shared Resources

Группа может иметь общий:

```text
money
items
vehicles
buildings
documents
equipment
information
territory
```

Но общий ресурс должен иметь правила доступа.

Например:

```text
TREASURY:
OFFICER+ can withdraw
MEMBER can deposit
```

---

# 30. Group Permissions

Минимальные разрешения:

```text
VIEW
USE
TAKE
TRANSFER
SELL
DESTROY
MODIFY
AUTHORIZE
```

Они должны определяться правилами организации.

---

# 31. Internal Conflict

Организация не должна быть единым сознанием.

Внутри могут существовать:

* разные цели;
* фракции;
* личные интересы;
* конфликты;
* секреты;
* борьба за власть.

Например:

```text
LEADERSHIP
vs
FIELD OPERATIVES
```

---

# 32. Betrayal

Предательство — обычное возможное действие.

Например:

```text
PLAYER A
является членом организации

PLAYER A
передаёт секрет другой фракции
```

Мир не должен запрещать это только потому, что:

```text
membership = true
```

Он должен оценить:

```text
rules
access
opportunity
consequences
```

---

# 33. Loyalty

Членство:

```text
MEMBERSHIP
```

не равно:

```text
LOYALTY
```

Персонаж может быть:

```text
MEMBER
+
LOW_LOYALTY
```

или:

```text
NON_MEMBER
+
HIGH_SYMPATHY
```

---

# 34. Multiplayer Reputation

Репутация может быть многослойной.

Не:

```text
REPUTATION = 73
```

а:

```text
REPUTATION:
settlement_A
faction_B
NPC_X
organization_C
public
criminal
scientific
```

Один игрок может считаться:

> надёжным исследователем

для одной группы и:

> опасным предателем

для другой.

---

# 35. Identity

Игрок имеет:

```text
ACCOUNT
```

а персонаж имеет:

```text
CHARACTER
```

И мир должен взаимодействовать именно с персонажем.

---

# 36. Player ≠ Character

Если человек:

```text
выходит из Telegram
```

персонаж не должен автоматически исчезать.

Он переходит в состояние:

```text
INACTIVE
```

или другое состояние мира.

---

# 37. Inactivity

Неактивность не должна автоматически означать:

```text
DEATH
```

Потому что это наказание игрока за отсутствие в реальной жизни.

Вместо этого возможны:

```text
INACTIVE
UNAVAILABLE
MISSING
HOSPITALIZED
CAPTURED
```

в зависимости от ситуации.

---

# 38. Absent Player

Если игрок отсутствует, нельзя позволять ИИ произвольно принимать важнейшие решения за него.

Например:

не:

> «Ваш персонаж решил предать друзей».

а:

```text
персонаж исчез
```

или:

```text
персонаж находится в плену
```

если это произошло по правилам мира.

---

# 39. Player-Controlled vs World-Controlled

Для важных действий должно быть понятно:

```text
PLAYER_CONTROLLED
```

или:

```text
WORLD_CONTROLLED
```

Если персонаж долго отсутствует, мир может управлять только теми аспектами, которые разрешены системой.

---

# 40. Multiplayer Social Layer

Игроки могут:

* говорить;
* спорить;
* торговать;
* создавать теории;
* обмениваться предметами;
* договариваться;
* лгать;
* объединяться;
* конфликтовать;
* помогать;
* предавать;
* создавать организации.

Это не «дополнительная социальная механика».

Это часть основного gameplay loop.

---

# 41. Telegram Group

Группа Telegram является:

```text
SOCIAL LAYER
```

а не самим миром.

В ней происходят:

* обсуждения;
* торговля;
* коллективные решения;
* публичные объявления;
* политические конфликты;
* теории;
* координация.

---

# 42. Telegram DM

Личные сообщения с ботом:

```text
PERSONAL WORLD INTERFACE
```

Здесь находятся:

* профиль;
* личная карта;
* личные знания;
* инвентарь;
* NPC;
* личные события;
* личные документы;
* приватные действия.

---

# 43. Public vs Private Action

Игрок может выполнить действие:

```text
PRIVATE
```

или:

```text
PUBLIC
```

Например:

```text
изучить документ
```

может быть приватным.

А:

```text
объявить результаты расследования
```

может стать публичным событием.

---

# 44. Multiplayer Investigation

Расследование может существовать:

```text
PERSONAL CASE
GROUP CASE
PUBLIC CASE
FACTION CASE
WORLD CASE
```

---

# 45. Personal Case

Только игрок знает:

```text
CASE
```

Он может не публиковать его.

---

# 46. Group Case

Несколько игроков работают над одной задачей.

У каждого могут быть разные:

```text
clues
documents
knowledge
interpretations
```

---

# 47. Public Case

Сообщество знает о существовании расследования.

Но отдельные доказательства могут оставаться приватными.

---

# 48. Shared Investigation State

Например:

```text
CASE_001

QUESTION:
Кто построил объект?

EVIDENCE:
A
B
C

THEORIES:
T1
T2
T3

STATUS:
OPEN
```

Игроки могут совместно изменять:

```text
evidence
theories
status
```

но не саму объективную истину.

---

# 49. Theory ≠ Canon

Игроки могут создать теорию:

> «Объект построила организация X».

Она существует как:

```text
THEORY
```

Даже если большинство игроков согласны.

Каноном она становится только при наличии соответствующего основания в системе мира.

---

# 50. Voting

Голосование может использоваться для:

* принятия решений внутри организации;
* выбора лидера;
* распределения ресурсов;
* социальных процессов.

Но голосование игроков не должно напрямую менять объективную истину мира.

Не:

```text
70% проголосовали,
что NPC виновен
↓
NPC действительно виновен
```

А:

```text
70% считают NPC виновным
↓
репутационное / политическое последствие
```

---

# 51. Majority ≠ Truth

Это особенно важно для WORLD//ERROR.

```text
PLAYER CONSENSUS
≠
WORLD TRUTH
```

Большинство может ошибаться.

И это может стать частью игры.

---

# 52. PvP

PvP должно существовать только там, где оно оправдано правилами мира.

Возможны:

```text
COMPETITION
THEFT
DECEPTION
POLITICAL CONFLICT
ECONOMIC WAR
ESPIONAGE
PHYSICAL CONFLICT
```

Но нельзя делать:

> «любой может в любой момент убить любого».

Это разрушит долгосрочную социальную структуру.

---

# 53. Conflict Permission

Для потенциально тяжёлых действий должны существовать условия:

```text
LOCATION
RELATIONSHIP
WEAPON
ACCESS
FACTION_STATUS
SECURITY
WITNESSES
WORLD_RULES
```

---

# 54. PvP Consequences

Если игрок атакует другого:

```text
ATTACK
↓
EVENT
↓
DAMAGE
↓
WITNESSES
↓
INFORMATION
↓
REPUTATION
↓
FACTION RESPONSE
```

То есть PvP является частью мира.

---

# 55. Murder Is Not a Button

Команда:

```text
/kill player
```

не должна существовать как простая административная операция.

Должна существовать модель:

```text
INTENT
→ ATTACK
→ CONDITIONS
→ RESOLUTION
→ CONSEQUENCES
```

---

# 56. Cooperation

Совместное действие может быть эффективнее одиночного.

Например:

```text
A:
исследование

B:
медицина

C:
охрана

D:
взлом
```

Вместе они могут выполнить операцию, невозможную одному игроку.

---

# 57. Complementary Knowledge

Особенно важен принцип:

> **Игроки должны иногда быть полезны друг другу именно потому, что знают разное.**

Например:

```text
A знает координаты.
B знает пароль.
C знает историю объекта.
D знает, кому принадлежит территория.
```

Только вместе:

```text
OPERATION POSSIBLE
```

---

# 58. Information Economy

Информация может иметь стоимость.

Игрок может сказать:

> «Я знаю, где находится объект».

И запросить:

* деньги;
* предмет;
* услугу;
* доступ;
* защиту;
* другую информацию;
* политическую поддержку.

---

# 59. Trust Economy

Но игрок может и соврать.

Поэтому существует:

```text
TRUST
```

и:

```text
VERIFICATION
```

Игроки постепенно создают социальную экономику доверия.

---

# 60. Meta-Game Problem

Игроки будут общаться вне игры.

Это неизбежно.

Они могут использовать:

* Telegram;
* Discord;
* Reddit;
* таблицы;
* базы знаний;
* скриншоты;
* внешние чаты.

Нельзя проектировать систему с предположением:

> «Игроки никогда не поделятся информацией».

---

# 61. Outside Information

Внешняя коммуникация не должна автоматически ломать игру.

Если игрок рассказал всем:

> «В комнате X есть объект Y»

то это уже социальная реальность.

Можно пытаться ограничивать:

```text OOC
```

и:

```text IC
```

но полностью разделить их невозможно.

---

# 62. IC / OOC

Нужно различать:

```text
IC
IN CHARACTER
```

и:

```text
OOC
OUT OF CHARACTER
```

Игрок может знать что-то как человек, но персонаж этого не знает.

---

# 63. Knowledge Boundary

Критический принцип:

> **Знание игрока не равно знанию персонажа.**

Игрок может прочитать:

```text
официальное сообщение в группе
```

Но персонаж должен узнать его только если он:

* увидел;
* услышал;
* получил сообщение;
* прочитал документ;
* узнал от NPC;
* участвовал в событии.

---

# 64. Но не нужно делать это мучительно

Не следует требовать:

> «Введи вручную всё, что твой персонаж знает».

Система должна сама отслеживать значимые знания.

Игроку достаточно взаимодействовать естественно.

---

# 65. Group Chat as World Layer

Если событие публичное:

```text
WORLD EVENT
```

бот может автоматически опубликовать:

```text
WORLD NEWS
```

Но публикация должна быть:

```text REPRESENTATION OF EVENT
```

а не самим событием.

---

# 66. News Delay

Информация не обязательно появляется мгновенно.

Например:

```text
EVENT:
09:00
```

```text
WITNESS:
09:03
```

```text
MESSAGE:
09:07
```

```text
PUBLIC NEWS:
09:40
```

Так возникает информационная динамика.

---

# 67. Local Knowledge

Не каждый регион знает всё.

Например:

```text
REGION A
знает о событии X
```

а:

```text
REGION B
ещё не знает.
```

Это позволяет создавать информационные границы.

---

# 68. Information Cascades

Один игрок сообщает:

```text
A → B
```

B:

```text
B → C
```

C:

```text
C → D
```

В процессе информация может:

```text
измениться
исказиться
дополниться
потерять источник
стать слухом
```

---

# 69. Multiplayer Rumor

Например:

```text
TRUTH:
объект закрыт.
```

Игрок A говорит:

> «Объект уничтожен».

Игрок B:

> «Говорят, он взорвался».

Игрок C:

> «Я слышал, что там был эксперимент».

Все три утверждения могут существовать одновременно.

---

# 70. Shared Discovery

Некоторые открытия требуют коллективного участия.

Например:

```text
REQUIRED:
3 independent observations
```

После этого:

```text
DISCOVERY STATUS:
SUPPORTED
```

Это создаёт естественную кооперацию.

---

# 71. Independence

Если 20 игроков услышали одно и то же от одного источника:

```text
20 reports
```

это не обязательно:

```text
20 independent confirmations
```

Источник один.

---

# 72. Collective Verification

Для некоторых открытий полезна модель:

```text
OBSERVATION A
+
OBSERVATION B
+
DOCUMENT C
↓
CORROBORATED
```

---

# 73. Shared Projects

Игроки могут строить:

* базы;
* лаборатории;
* дороги;
* организации;
* архивы;
* торговые сети;
* исследовательские проекты.

Такие проекты требуют:

```text
resources
time
people
knowledge
coordination
```

---

# 74. Project State

Например:

```text
PROJECT:
RADIO TOWER

PROGRESS:
62%

RESOURCES:
steel
electronics
labor

RISKS:
storm
sabotage
shortage
```

Разные игроки могут вносить вклад.

---

# 75. Contribution

Вклад может быть:

```text
MATERIAL
LABOR
KNOWLEDGE
MONEY
INFORMATION
REPUTATION
RISK
TIME
```

Не только деньги.

---

# 76. Collective Failure

Проект может провалиться.

Причины:

```text
недостаток ресурсов
саботаж
ошибка
конфликт
нападение
неверная теория
```

Провал тоже должен становиться историей.

---

# 77. Shared Infrastructure

Если игроки построили:

```text
RADIO STATION
```

она становится частью общего мира.

Другие игроки могут:

* использовать;
* атаковать;
* покупать доступ;
* ремонтировать;
* захватывать;
* улучшать.

---

# 78. Ownership

Право собственности должно быть отдельным состоянием:

```text
OWNER
CONTROL
ACCESS
USAGE
```

Например:

```text
Faction A:
OWNER

Faction B:
CONTROL

Player C:
ACCESS

Player D:
NO ACCESS
```

---

# 79. Social Power

В multiplayer сила игрока не должна определяться только боевыми характеристиками.

Она может исходить из:

```text
KNOWLEDGE
REPUTATION
RELATIONSHIPS
MONEY
ORGANIZATION
ACCESS
INFLUENCE
TERRITORY
TECHNOLOGY
INFORMATION
```

---

# 80. No Single Optimal Role

Игрок может стать:

* исследователем;
* торговцем;
* дипломатом;
* разведчиком;
* врачом;
* инженером;
* криминальным посредником;
* лидером организации;
* архивистом;
* журналистом;
* контрабандистом;
* картографом;
* политическим игроком.

Это не классы.

Это роли, которые возникают из действий.

---

# 81. Player Specialization

Специализация должна возникать из:

```text
repeated actions
knowledge
relationships
equipment
reputation
history
```

а не обязательно из выбора:

> «Выберите класс».

---

# 82. Social Memory

Игроки должны существовать в памяти мира.

Например:

```text
CHARACTER:
X

KNOWN FOR:
- expedition
- discovery
- betrayal
- organization
```

Это может влиять на NPC и фракции.

---

# 83. Death and Multiplayer

После смерти:

```text
CHARACTER = DEAD
```

Но:

```text
WORLD CONSEQUENCES = REMAIN
```

Другие игроки могут помнить персонажа.

---

# 84. New Character

Новый персонаж:

```text
NEW IDENTITY
```

но:

```text
SAME WORLD
```

Он может узнать:

> «До тебя здесь был исследователь, который исчез».

И даже не знать, что это был предыдущий персонаж того же игрока.

---

# 85. Anti-Meta Abuse

Нельзя позволять игроку использовать смерть персонажа как бесплатный способ сбросить последствия.

Например:

```text
CHARACTER A
совершил преступление
↓
умер
↓
CHARACTER B
полностью чист
```

На уровне персонажа — возможно.

На уровне мира:

```text
HISTORY
```

остаётся.

---

# 86. Character Continuity

Если новый персонаж связан с прошлым:

```text
родственник
ученик
коллега
член организации
```

это может быть частью истории.

Но не должно автоматически переносить:

```text
весь inventory
всю knowledge
```

---

# 87. Multiplayer Population

Количество игроков должно учитываться как состояние мира.

Например:

```text
POPULATION
ACTIVE
INACTIVE
MISSING
DEAD
```

Это может влиять на:

* экономику;
* NPC;
* поселения;
* безопасность;
* спрос;
* политику.

---

# 88. Player Density

Если в одной локации слишком много игроков:

```text
PLAYER DENSITY ↑
```

могут возникнуть:

* очереди;
* шум;
* дефицит;
* социальные события;
* конфликты;
* возможности торговли.

Но система не должна искусственно телепортировать игроков только ради балансировки.

---

# 89. Anti-Griefing

Постоянный мир требует защиты от разрушительного поведения.

Нужно различать:

```text
LEGITIMATE CONFLICT
```

и:

```text
GRIEFING
```

Например, если игрок уничтожает объект ради разумной цели — это часть игры.

Если он пытается:

```text
ломать систему
спамить действиями
бесконечно создавать мусорные события
```

это уже техническая проблема.

---

# 90. Action Limits

Ограничения должны быть не только:

```text
cooldown
```

Можно использовать:

```text
resources
time
energy
access
risk
attention
social consequences
```

Игрок должен быть ограничен миром, а не только таймером.

---

# 91. Spam Resistance

Telegram позволяет отправлять много сообщений.

Поэтому:

```text
MESSAGE ≠ ACTION
```

Например:

```text
"ударяю"
"ударяю"
"ударяю"
"ударяю"
```

не должно автоматически создавать четыре атаки.

Система должна распознавать:

```text
intent
```

и разрешать действие по правилам.

---

# 92. Command Determinism

Для критических действий желательно иметь структурированную форму:

```text
/attack target
/travel location
/trade item amount
/investigate object
```

AI может помогать преобразовать естественную речь:

> «Я хочу попробовать договориться с охранником и предложить ему деньги».

в:

```text
INTENT:
NEGOTIATE

TARGET:
GUARD

OFFER:
MONEY
```

Но итог определяет движок.

---

# 93. AI in Multiplayer

AI может:

* понимать намерение;
* вести NPC;
* форматировать ответы;
* помогать анализировать документы;
* генерировать варианты диалога;
* объяснять доступные действия.

AI не должен:

* самостоятельно менять канон;
* выдавать несуществующие ресурсы;
* создавать факты;
* произвольно решать исход критических конфликтов.

---

# 94. Fairness

В multiplayer невозможно сделать так, чтобы все игроки получили одинаковый опыт.

Цель:

> **не одинаковость, а понятность правил.**

Игрок может проиграть.

Но он должен понимать:

```text
почему это было возможно
```

хотя бы потенциально.

---

# 95. Hidden Information Is Not Cheating

Если игрок не знает:

```text
NPC_SECRET
```

это не несправедливость.

Если он мог узнать это через игру, это:

```text
DISCOVERY OPPORTUNITY
```

---

# 96. No Forced Equality

Не нужно автоматически уравнивать:

```text
богатство
репутацию
влияние
знания
```

Если игроки годами играют:

```text
A:
лидер организации

B:
новичок
```

это нормально.

Мир должен поддерживать социальную динамику.

---

# 97. Catch-Up

При этом новый игрок должен иметь возможность встроиться в мир.

Он не должен смотреть:

> «Старожилы играют два года, значит мне нечего делать».

Новые возможности могут возникать из:

* новых регионов;
* новых конфликтов;
* новых профессий;
* новых организаций;
* новых исследований;
* смены поколений;
* новых исторических периодов.

---

# 98. Player-Generated Content

Игроки могут создавать:

```text
organizations
documents
maps
theories
archives
businesses
settlements
rituals
stories
```

Но:

```text
CREATED BY PLAYER
≠
CANON
```

---

# 99. Community Canonization

Некоторые элементы могут постепенно становиться частью мира:

```text
IDEA
↓
COMMUNITY
↓
SUPPORTED
↓
CANON
```

Решение остаётся за автором/системой канона.

---

# 100. Multiplayer History

История мира должна содержать:

```text
PLAYER EVENTS
NPC EVENTS
FACTION EVENTS
WORLD EVENTS
COMMUNITY EVENTS
```

Это позволяет спустя год сказать:

> «Вот что произошло».

---

# 101. Historical Perspective

Игрок, пришедший позже, может изучать прошлое через:

* архивы;
* документы;
* NPC;
* руины;
* новости;
* старые сообщения;
* памятники;
* предметы;
* организации.

Так прошлое не исчезает вместе с игроками.

---

# 102. World Continuity

Если:

```text
PLAYER A
изменил мир
```

то:

```text
PLAYER B
```

должен жить уже в изменённом мире.

Это основной тест multiplayer-системы.

---

# 103. Multiplayer Core Loop

```text
PLAYER
↓
OBSERVE
↓
ACT
↓
WORLD CHANGES
↓
OTHER PLAYERS EXPERIENCE CHANGE
↓
INFORMATION SPREADS
↓
PLAYERS INTERPRET
↓
COOPERATE / COMPETE
↓
NEW ACTIONS
↓
WORLD CHANGES AGAIN
```

---

# 104. Главный принцип

> **Мультиплеер WORLD//ERROR — это не когда много игроков получают один и тот же контент. Это когда много людей одновременно создают историю одного мира.**

---

# 105. Второй принцип

> **Разные игроки должны иметь разные знания, но жить в одном объективном мире.**

---

# 106. Третий принцип

> **Игрок может ошибаться. Его персонаж может ошибаться. Сообщество может ошибаться. Но движок мира не должен путать ошибку игрока с истиной мира.**

---

# 107. Четвёртый принцип

> **Любое значимое коллективное действие должно иметь единую точку истины в WORLD ENGINE.**

Не:

```text
Telegram says X
```

а:

```text
WORLD STATE = X
Telegram REPRESENTS X
```

---

# 108. Пятый принцип

> **Игроки не должны быть зрителями одного сюжета. Они должны быть причинами новых состояний мира.**

---

# 109. Итоговая архитектура multiplayer

```text
                 WORLD ENGINE
                      │
          ┌───────────┼───────────┐
          │           │           │
        WORLD       GROUP       PLAYER
          │           │           │
          │           │           │
       EVENTS      ACTIONS     KNOWLEDGE
          │           │           │
          └───────┬───┴───────────┘
                  │
             CONSEQUENCES
                  │
             WORLD STATE
                  │
        ┌─────────┴─────────┐
        │                   │
    TELEGRAM GROUP       TELEGRAM DM
        │                   │
   SOCIAL LAYER        PERSONAL LAYER
```

---

# 110. Финальная формула

```text
ONE WORLD
+
MANY CHARACTERS
+
ASYMMETRIC KNOWLEDGE
+
PLAYER AGENCY
+
SHARED CONSEQUENCES
+
SOCIAL INTERACTION
+
PERSISTENT HISTORY
=
WORLD//ERROR MULTIPLAYER
```

И самое важное:

> **Игрок не должен чувствовать, что другие игроки находятся рядом только потому, что так устроен Telegram-чат. Он должен чувствовать, что они действительно живут в том же мире.**
