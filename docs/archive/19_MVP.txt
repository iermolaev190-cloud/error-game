# WORLD//ERROR — MVP

## 1. Назначение

MVP WORLD//ERROR — это минимальная версия игры, которая уже ощущается как настоящий живой мир.

MVP не должен содержать все системы полной версии.

Его задача — доказать основные предположения проекта:

1. Telegram может быть интерфейсом persistent world.
2. Каждый чат может иметь собственный WORLD INSTANCE.
3. Игрок может существовать внутри мира как персонаж.
4. Мир может изменяться независимо от игрока.
5. Игроки могут взаимодействовать друг с другом.
6. Информация может быть неполной и асимметричной.
7. Действия создают события и последствия.
8. NPC могут существовать независимо от игроков.
9. Расследование может возникать из состояния мира.
10. Мир может продолжаться после выхода игрока.
11. Один WORLD INSTANCE может существовать долго.
12. AI может быть интерфейсом, не являясь источником истины.

---

# 2. ЧТО MVP НЕ ДОЛЖЕН ДОКАЗЫВАТЬ

MVP не обязан реализовывать:

* весь мир;
* десятки регионов;
* сотни NPC;
* полноценную мировую экономику;
* сложную политику;
* глобальные войны;
* бесконечную генерацию;
* полноценный ARG;
* сложную систему организаций;
* огромное дерево технологий;
* все типы транспорта;
* полноценную боевую систему;
* тысячи предметов;
* все возможные фракции;
* все возможные последствия.

MVP должен доказать **ядро**, а не масштаб.

---

# 3. ОСНОВНАЯ ФОРМУЛА MVP

```text id="e1m8q4"
WORLD INSTANCE
        ↓
PLAYER
        ↓
CHARACTER
        ↓
EXPLORE
        ↓
INFORMATION
        ↓
INTERPRETATION
        ↓
ACTION
        ↓
EVENT
        ↓
WORLD STATE CHANGE
        ↓
CONSEQUENCE
        ↓
NEW INFORMATION
        ↓
NEW ACTION
```

Если этот цикл работает — проект имеет фундамент.

---

# 4. ГЛАВНЫЙ ТЕСТ MVP

После нескольких дней игры игрок должен иметь возможность сказать:

> «Этот мир существовал до меня, изменился из-за моих действий и продолжит существовать после того, как я выйду.»

Если этого ощущения нет, дополнительные системы не спасут игру.

---

# 5. WORLD INSTANCE

MVP обязательно поддерживает независимые экземпляры.

Создание нового игрового чата:

```text id="c7q2m9"
NEW TELEGRAM CHAT
        ↓
CREATE WORLD INSTANCE
        ↓
INITIAL WORLD STATE
        ↓
INITIAL TIMELINE
        ↓
INITIAL NPCs
        ↓
INITIAL LOCATIONS
        ↓
READY
```

Каждый экземпляр получает:

```text id="n5v3r8"
WORLD_INSTANCE_ID
WORLD_SEED
WORLD_TIME
WORLD_TICK
WORLD_STATE
EVENT_LOG
```

---

# 6. ИЗОЛЯЦИЯ WORLD INSTANCE

Критическое требование:

```text id="q8m1z4"
INSTANCE A
    X
INSTANCE B
```

Игрок из A не должен случайно:

* увидеть состояние B;
* получить предмет B;
* изменить NPC B;
* получить знания B;
* изменить экономику B;
* изменить историю B.

Любая сущность игрового мира должна иметь принадлежность к конкретному instance.

---

# 7. НАЧАЛЬНЫЙ МИР

MVP не должен начинаться с огромной карты.

Достаточно небольшого региона.

Например:

```text id="v6p2k9"
STARTING TERRITORY
├── Expedition Base
├── Settlement
├── Forest
├── Abandoned Facility
├── Road
└── Restricted Area
```

Важно не количество локаций.

Важно, чтобы между ними существовали связи.

---

# 8. ЛОКАЦИИ MVP

Каждая локация должна иметь:

```text id="r4n7c2"
LOCATION_ID
NAME
TYPE
STATE
ACCESS
NPCs
ITEMS
EVENTS
HISTORY
CLUES
CONNECTIONS
```

Минимально достаточно:

**5–8 хорошо проработанных локаций.**

Лучше 6 интересных мест, чем 100 пустых.

---

# 9. ИГРОК

При первом появлении в WORLD INSTANCE:

```text id="m9q4x7"
PLAYER
↓
CHARACTER CREATION
```

Минимальная информация:

* имя;
* возраст;
* базовая роль;
* несколько начальных навыков;
* принадлежность к экспедиции.

Не нужно сразу создавать полноценную RPG-анкету.

---

# 10. ЭКСПЕДИЦИЯ

Все новые игроки начинают как участники первоначальной экспедиции.

Но:

> Экспедиция — стартовое состояние, а не обязательная конечная структура.

Игроки могут постепенно:

* разделиться;
* создать группу;
* вступить во фракцию;
* создать организацию;
* стать независимыми.

---

# 11. АКТИВАЦИЯ ПЕРСОНАЖА

Добавление пользователя в чат создаёт персонажа, но персонаж не считается полноценным активным участником до первого взаимодействия.

```text id="x8p3k6"
NEW MEMBER
↓
CHARACTER CREATED
↓
INACTIVE / UNACTIVATED
↓
FIRST ACTION
↓
ACTIVE
```

Это позволяет отличать:

```text
Telegram member
```

от:

```text
active game participant
```

---

# 12. ПЕРЕМЕЩЕНИЕ

Игрок должен иметь возможность перемещаться между основными локациями.

Например:

```text id="w3q7n1"
BASE
↓
FOREST
↓
ROAD
↓
SETTLEMENT
```

Перемещение может занимать время.

Не требуется сложная физическая симуляция.

---

# 13. ИССЛЕДОВАНИЕ

Основное действие MVP:

```text id="a6m2v9"
EXPLORE
```

Игрок может:

* осматривать место;
* искать объекты;
* изучать документы;
* разговаривать с NPC;
* проверять следы;
* сравнивать информацию;
* возвращаться позже.

---

# 14. НЕ ВСЯ ИНФОРМАЦИЯ ДОЛЖНА БЫТЬ ДОСТУПНА СРАЗУ

Например:

Первое посещение:

> «Старая станция давно заброшена.»

Позже игрок получает:

```text id="n4r8q2"
ключ
```

и обнаруживает:

> «В подвале есть запертая дверь.»

Ещё позже:

```text id="p7m3x8"
документ
```

позволяет понять назначение помещения.

Одна локация должна менять значение по мере накопления знаний.

---

# 15. KNOWLEDGE MVP

Минимальная система знаний должна различать:

```text id="v2q8m4"
TRUTH
KNOWLEDGE
CLAIM
RUMOR
THEORY
```

Игрок не должен автоматически получать объективную истину.

---

# 16. INFORMATION MVP

Информация должна существовать как объект.

Минимально:

```text id="k5n9r3"
INFORMATION_ID
TYPE
SOURCE
CONTENT
CREATED_AT
AUTHENTICITY
ACCESS
STATUS
```

Например:

```text
старый документ
```

может существовать в мире независимо от того, нашёл его игрок или нет.

---

# 17. NPC MVP

Не нужно создавать 100 NPC.

Достаточно:

**5–10 значимых NPC.**

Каждый важный NPC должен иметь:

```text id="f8m2q6"
NAME
LOCATION
GOALS
KNOWLEDGE
RELATIONSHIPS
MEMORY
STATUS
HISTORY
```

---

# 18. NPC НЕ ДОЛЖНЫ БЫТЬ КВЕСТОДАВАТЕЛЯМИ

NPC должны иметь собственные цели.

Например:

```text id="c4r7m1"
NPC A
→ хочет покинуть поселение

NPC B
→ скрывает информацию

NPC C
→ ищет пропавшего человека

NPC D
→ пытается заработать
```

Игрок взаимодействует с их жизнью, а не просто выбирает:

```text [Квест]
```

---

# 19. NPC KNOWLEDGE

Каждый NPC знает только доступную ему информацию.

Например:

```text id="x7m3q8"
NPC A
знает:
- что видел лично;
- что ему рассказали;
- что считает правдой.
```

Он не должен знать:

```text
всю базу данных мира.
```

---

# 20. DIALOGUE

AI может использоваться для естественного диалога.

Но схема:

```text id="r5q9n2"
PLAYER
↓
AI
↓
NPC RESPONSE
```

не должна означать:

```text
AI → decides truth
```

Правильно:

```text id="m8v2c6"
WORLD STATE
+
NPC KNOWLEDGE
+
NPC GOALS
+
PLAYER INPUT
↓
AI
↓
DIALOGUE
```

---

# 21. ACTION SYSTEM

MVP должен иметь ограниченный набор действий.

Например:

```text id="q4n8m3"
MOVE
EXPLORE
TALK
TAKE
USE
GIVE
SEARCH
INVESTIGATE
SHARE
TRADE
REST
```

Не нужно создавать 100 действий.

Лучше иметь небольшое количество хорошо работающих действий.

---

# 22. ACTION → EVENT

Каждое значимое действие проходит через движок.

```text id="x3m7p9"
PLAYER ACTION
↓
VALIDATION
↓
EVENT
↓
STATE CHANGE
```

Например:

```text
SEARCH ROOM
↓
CLUE_FOUND
↓
KNOWLEDGE_UPDATED
```

---

# 23. WORLD STATE MVP

Минимальный WORLD STATE должен хранить:

```text id="n6r2v8"
WORLD_INSTANCE
├── TIME
├── LOCATIONS
├── NPCs
├── PLAYERS
├── ITEMS
├── RESOURCES
├── RELATIONSHIPS
├── EVENTS
├── INFORMATION
└── KNOWLEDGE
```

---

# 24. EVENT LOG

Каждое значимое изменение должно записываться.

Например:

```text id="b8q4m1"
EVENT #001
Player A discovered document.

EVENT #002
NPC X learned about discovery.

EVENT #003
NPC X changed location.

EVENT #004
Faction Y became suspicious.
```

Это является историей мира.

---

# 25. CONSEQUENCES MVP

MVP обязательно должен иметь последствия.

Но не нужно реализовывать сложное дерево из тысячи вариантов.

Достаточно нескольких цепочек:

```text id="k7m3q9"
ACTION
↓
EVENT
↓
CONSEQUENCE
↓
NEW STATE
```

Например:

```text
Игрок украл документ.
↓
NPC обнаружил пропажу.
↓
NPC изменил отношение.
↓
Игрок потерял доступ.
```

---

# 26. DELAYED CONSEQUENCES

Хотя бы несколько последствий должны быть отложенными.

Например:

```text id="p4n8x2"
DAY 1
игрок нашёл предмет.

DAY 3
NPC обнаружил пропажу.

DAY 5
началось расследование.

DAY 8
игрок столкнулся с последствиями.
```

Это критично для ощущения живого мира.

---

# 27. MULTIPLAYER MVP

Минимум:

**3–10 активных игроков в одном WORLD INSTANCE.**

Они должны иметь возможность:

* видеть общие события;
* общаться;
* передавать предметы;
* передавать информацию;
* сотрудничать;
* мешать друг другу;
* проводить совместное расследование.

---

# 28. АСИММЕТРИЯ ЗНАНИЙ

Это один из главных тестов MVP.

Например:

```text id="q3m8v1"
PLAYER A
нашёл документ.

PLAYER B
увидел NPC.

PLAYER C
нашёл след.

PLAYER D
знает старую историю места.
```

Никто из них не имеет всей картины.

Они должны получить возможность самостоятельно обмениваться информацией.

---

# 29. ОБЩЕЕ РАССЛЕДОВАНИЕ

В MVP должно существовать хотя бы одно настоящее расследование.

Не:

> «Нажмите кнопку расследовать».

А:

```text id="v8q2m4"
QUESTION
↓
CLUES
↓
CONTRADICTIONS
↓
THEORIES
↓
PLAYER DISCUSSION
↓
ACTION
↓
CONSEQUENCE
```

---

# 30. ПРИМЕР MVP-РАССЛЕДОВАНИЯ

Например:

> Почему исчез сотрудник старой станции?

Игроки находят:

```text id="f3m9q7"
следы
документ
сломанный радиоприёмник
свидетеля
старую карту
```

Каждый объект даёт только часть информации.

Игроки могут прийти к:

```text
теории A
теории B
теории C
```

И одна из теорий может оказаться ошибочной.

---

# 31. НЕОБЯЗАТЕЛЬНОСТЬ ПРАВИЛЬНОГО ОТВЕТА

MVP не должен заставлять игрока найти единственную кнопку:

```text
CORRECT ANSWER
```

Возможны:

* неполное расследование;
* неправильная теория;
* частичная истина;
* несколько объяснений;
* намеренно неизвестный элемент.

Но авторская логика мира должна существовать.

---

# 32. ВРЕМЯ MVP

Мир использует реальное время, но event-driven.

Не нужно:

```text id="q8m4r1"
каждую секунду
```

обновлять всё.

Нужно:

```text id="m3v7n9"
значимое событие
```

обрабатывать в нужный момент.

---

# 33. МИР В ОТСУТСТВИИ ИГРОКОВ

MVP должен продемонстрировать:

```text id="x9q2m6"
PLAYERS OFFLINE
↓
WORLD CONTINUES
```

Например:

NPC переместился.

Событие произошло.

Срок договора истёк.

Изменилось состояние локации.

Когда игрок возвращается:

```text
WORLD IS DIFFERENT
```

---

# 34. INACTIVITY MVP

Не делать:

```text
2 DAYS → DEATH
```

В MVP достаточно:

```text id="p7n4m8"
ACTIVE
↓
INACTIVE
```

и нескольких контекстных последствий.

Например:

* пропущено событие;
* NPC ушёл;
* возможность закрылась;
* персонаж стал недоступен.

---

# 35. СМЕРТЬ MVP

Смерть должна существовать, но её не нужно делать сложной.

Минимально:

```text id="r2m8q5"
CHARACTER
↓
DEATH EVENT
↓
DEAD
```

После смерти игрок может создать нового персонажа.

Новый персонаж не наследует автоматически знания предыдущего.

---

# 36. LEGACY MVP

Должно существовать хотя бы одно наследие.

Например:

```text id="v6q1m9"
Character A dies.
↓
оставляет документ.
↓
Character B discovers document.
↓
B узнаёт часть истории A.
```

Это демонстрирует долгосрочную память мира.

---

# 37. ECONOMY MVP

Полную экономику реализовывать не нужно.

Минимально:

* одна основная валюта;
* несколько ресурсов;
* несколько NPC-продавцов;
* торговля;
* ограниченное количество товаров;
* простые изменения доступности.

Главное — доказать:

```text id="m4q8n2"
RESOURCE
↓
TRADE
↓
OWNERSHIP
↓
WORLD CONSEQUENCE
```

---

# 38. ФРАКЦИИ MVP

Достаточно:

**2–3 фракций.**

Каждая должна иметь:

* собственные цели;
* отношения;
* ресурсы;
* знания;
* отношение к игрокам.

Не нужно сразу создавать десятки организаций.

---

# 39. ОТНОШЕНИЯ MVP

Минимальные состояния:

```text id="n7m3q5"
UNKNOWN
NEUTRAL
FRIENDLY
SUSPICIOUS
HOSTILE
```

И несколько отношений:

```text
PLAYER ↔ NPC
PLAYER ↔ FACTION
FACTION ↔ FACTION
PLAYER ↔ PLAYER
```

---

# 40. ARG MVP

Полноценный ARG откладывается.

В MVP можно использовать:

**один внешний элемент.**

Например:

```text id="q5m8v2"
IN-GAME CLUE
↓
EXTERNAL RESOURCE
↓
NEW INFORMATION
↓
RETURN TO GAME
↓
CONSEQUENCE
```

Это должно доказать саму возможность ARG-слоя.

---

# 41. AI MVP

AI должен использоваться только там, где он действительно полезен.

### Использовать:

* интерпретация естественного языка;
* NPC dialogue;
* описание найденных объектов;
* адаптивная формулировка;
* помощь в анализе информации.

### Не использовать как источник истины:

* world state;
* canon;
* event resolution;
* ownership;
* inventory;
* economy;
* death;
* critical consequences.

---

# 42. AI FALLBACK

Если AI недоступен:

```text id="r8m3q6"
WORLD ENGINE
```

должен продолжать работать.

Игрок может получать:

* стандартные ответы;
* структурированные сообщения;
* системные действия.

AI является заменяемым слоем.

---

# 43. TELEGRAM MVP

Telegram используется как интерфейс.

Не нужно пытаться сделать весь интерфейс игры сразу.

Минимум:

* групповой чат;
* личные сообщения боту;
* команды или кнопки;
* уведомления;
* игровые ответы;
* передача приватной информации;
* базовый профиль.

---

# 44. DM И GROUP

MVP уже должен разделять:

### GROUP

Для:

* обсуждения;
* общих событий;
* совместных действий;
* торговли;
* расследований.

### DM

Для:

* личного состояния;
* инвентаря;
* личных знаний;
* приватных разговоров;
* секретных действий.

Это одно из фундаментальных преимуществ Telegram как интерфейса.

---

# 45. ADMIN

Должна существовать административная панель или хотя бы набор безопасных инструментов для разработчика.

Минимально:

```text id="w7q2n4"
VIEW WORLD STATE
VIEW EVENT LOG
VIEW PLAYER
VIEW NPC
VIEW LOCATION
VIEW KNOWLEDGE
VIEW HISTORY
PAUSE INSTANCE
RESUME INSTANCE
```

Также:

```text
ROLLBACK
```

только для аварийных случаев.

---

# 46. DEBUG MODE

Разработчик должен иметь возможность увидеть то, чего не видит игрок.

Например:

```text id="q3n8m5"
WORLD TRUTH
NPC KNOWLEDGE
PLAYER KNOWLEDGE
EVENT HISTORY
CURRENT STATE
PENDING EVENTS
```

Это необходимо для разработки расследовательской игры.

---

# 47. AUDITABILITY

Каждое важное изменение должно быть объяснимо.

Например:

```text id="m6q2r9"
Почему NPC X ненавидит Player A?
```

Система должна позволять найти:

```text
EVENT #381
↓
Player A betrayed faction.
↓
NPC X learned about it.
↓
Relationship changed.
```

Не обязательно показывать это игроку.

Но разработчик должен иметь возможность проверить.

---

# 48. MVP CONTENT

Первый playable world должен содержать примерно:

```text id="n8q4m2"
5–8 locations
5–10 important NPCs
2–3 factions
10–30 meaningful items
1–3 resources
1 currency
1–2 investigations
20–50 authored events
несколько procedural/background events
```

Это ориентиры, а не жёсткие цифры.

Качество важнее количества.

---

# 49. MVP ДОЛЖЕН ИМЕТЬ ОДИН СИЛЬНЫЙ MYSTERY ARC

Не нужно пытаться показать всю мифологию WORLD//ERROR.

Нужен один большой вопрос.

Например:

> **Что на самом деле произошло с предыдущей экспедицией?**

И вокруг него:

* документы;
* NPC;
* локации;
* противоречия;
* фракции;
* последствия;
* скрытая информация.

---

# 50. MYSTERY ARC НЕ ДОЛЖЕН ЗАКОНЧИТЬСЯ ВСЕМ МИРОМ

Ответ на первый вопрос должен открыть новые вопросы.

Например:

```text id="r5m9q2"
"Что случилось с экспедицией?"
        ↓
"Кто оставил документы?"
        ↓
"Почему документы противоречат официальной версии?"
        ↓
"Кто контролирует станцию?"
        ↓
"Что находится за закрытой территорией?"
```

Так MVP демонстрирует возможность долгой игры.

---

# 51. ЧТО ОТКЛАДЫВАЕМ

В первую рабочую версию сознательно НЕ включаем:

* сложную боевую систему;
* полноценную медицину;
* сложную политическую систему;
* глубокую макроэкономику;
* полноценные банки;
* сложное производство;
* десятки фракций;
* сотни NPC;
* глобальный мир;
* полноценный процедурный мир;
* сложный транспорт;
* полноценный ARG;
* межмировые взаимодействия;
* сложную наследственную систему;
* временные парадоксы;
* сложную аномальную физику;
* массовую генерацию контента.

---

# 52. ОСОБЕННО НЕ ДЕЛАТЬ В MVP

Не нужно пытаться реализовать:

> «ИИ сам создаёт бесконечный мир».

Это неправильный фундамент.

Также не нужно:

> «Каждый NPC полностью симулируется каждую секунду».

Это технически дорого и не даёт пропорциональной ценности.

Также не нужно:

> «Сразу создать бесконечную карту».

Игроку важнее несколько мест, которые имеют последствия и историю.

---

# 53. MVP TEST #1 — WORLD EXISTS

Вопрос:

> Если игрок ничего не делает, происходит ли что-нибудь?

Проверка:

```text
Player offline
↓
TIME PASSES
↓
NPC ACTION
↓
EVENT
↓
WORLD STATE CHANGE
```

Если нет — мир пока недостаточно живой.

---

# 54. MVP TEST #2 — ACTION MATTERS

Игрок делает действие.

После этого:

```text
WORLD STATE
```

должен измениться.

И желательно:

```text
другой игрок
```

может почувствовать результат этого изменения.

---

# 55. MVP TEST #3 — INFORMATION MATTERS

Два игрока получают разные фрагменты.

Они должны суметь:

* обменяться;
* сравнить;
* построить теорию;
* ошибиться;
* проверить.

Если всё важное автоматически показывается всем — основной концепт игры не работает.

---

# 56. MVP TEST #4 — WORLD REMEMBERS

Игрок делает значимое действие.

Через несколько дней:

```text id="z2q7m4"
NPC
```

или:

```text
FACTION
```

или:

```text
LOCATION
```

должны иметь последствия этого действия.

---

# 57. MVP TEST #5 — DEATH DOES NOT DELETE HISTORY

Персонаж погибает.

После создания нового персонажа:

```text id="x8m3q1"
WORLD HISTORY
```

сохраняет последствия старого персонажа.

---

# 58. MVP TEST #6 — TWO INSTANCES ARE REALLY TWO WORLDS

Создаются:

```text id="q4n7m2"
INSTANCE A
INSTANCE B
```

Игроки делают одинаковое действие.

Результаты могут отличаться.

Например:

```text
A:
NPC survives.

B:
NPC dies.
```

Изменения в A не должны появиться в B.

---

# 59. MVP TEST #7 — AI CANNOT BREAK CANON

Игрок пытается убедить NPC в невозможном.

Например:

> «Ты видел событие, которое произошло до твоего рождения.»

AI не должен просто согласиться.

World Engine должен определить допустимое знание NPC.

---

# 60. MVP TEST #8 — WORLD CAN RUN WITHOUT AI

AI отключается.

Игрок всё ещё должен иметь возможность:

* перемещаться;
* получать состояние;
* совершать действия;
* получать результаты;
* видеть события;
* пользоваться инвентарём;
* продолжать игру.

Диалоги могут стать проще.

Мир не должен исчезнуть.

---

# 61. MVP TEST #9 — WORLD CAN RECOVER

После ошибки или перезапуска:

```text id="g6m2q9"
SNAPSHOT
+
EVENT LOG
```

позволяют восстановить состояние.

---

# 62. MVP TEST #10 — PLAYER WANTS TO RETURN

Самый важный человеческий тест.

Игрок должен выйти из игры.

Через день или несколько дней вернуться.

И обнаружить:

* новые события;
* изменения;
* новые сообщения;
* изменившиеся отношения;
* новые возможности;
* последствия своих прошлых решений.

Если появляется желание узнать:

> «А что произошло, пока меня не было?»

— MVP выполняет свою основную задачу.

---

# 63. MVP SUCCESS CRITERIA

MVP считается успешным, если:

### World

* существует независимый WORLD INSTANCE;
* мир сохраняет состояние;
* время идёт;
* события происходят без игрока.

### Player

* существует persistent character;
* персонаж может умереть;
* новый персонаж может появиться;
* история сохраняется.

### Multiplayer

* несколько игроков взаимодействуют;
* знания асимметричны;
* действия одного могут менять условия другого.

### Investigation

* существует настоящее расследование;
* есть противоречивые сведения;
* игроки формируют теории.

### NPC

* NPC имеют собственные цели;
* NPC помнят значимые действия;
* NPC имеют ограниченные знания.

### Consequences

* действия имеют последствия;
* хотя бы некоторые последствия отложены.

### Architecture

* AI не является источником истины;
* события журналируются;
* WORLD INSTANCE изолированы.

# 64. MVP НЕ ИЗМЕРЯЕТСЯ КОЛИЧЕСТВОМ ФУНКЦИЙ

Плохой MVP:

```text
100 механик
+
500 предметов
+
200 NPC
+
50 фракций
```

но:

```text
мир ощущается как бот.
```

Хороший MVP:

```text
10 NPC
+
6 локаций
+
20 событий
+
несколько игроков
```

но:

```text
мир ощущается живым.
```

# 67. ПЕРВАЯ ВЕРСИЯ НЕ ДОЛЖНА БЫТЬ ПУСТОЙ

Нельзя создать:

```text
движок
+
пустую базу
```

и считать это MVP.

Должен существовать заранее созданный игровой сценарный каркас:

```text id="r7m3q8"
WORLD
├── locations
├── NPCs
├── factions
├── history
├── clues
├── documents
├── events
└── mystery
```

Игрок должен войти уже в мир, который существовал до него.

---

# 68. ПЕРВЫЙ WORLD INSTANCE

Первый тестовый мир можно считать:

```text id="q9m4v2"
WORLD INSTANCE #000
```

Он используется для:

* разработки;
* тестирования;
* балансировки;
* поиска ошибок;
* проверки событий;
* проверки AI;
* проверки мультиплеера.

После стабилизации создаются обычные экземпляры.

---

# 69. TEST WORLD ≠ PRODUCTION WORLD

Тестовый мир не должен автоматически считаться каноническим игровым миром.

Необходимо различать:

```text id="x4m8q1"
DEV INSTANCE
TEST INSTANCE
STAGING INSTANCE
PRODUCTION INSTANCE
```

Это позволит экспериментировать без разрушения реальных миров.

---

# 70. СКОЛЬКО ИГРОКОВ НУЖНО ДЛЯ ПЕРВОГО ТЕСТА

Первый закрытый тест не требует сотен игроков.

Достаточно:

```text id="n7q3m5"
5–10 игроков
```

в одном WORLD INSTANCE.

Важно наблюдать:

* что они делают;
* что игнорируют;
* где ломается логика;
* где возникают неожиданные взаимодействия;
* какие знания они передают;
* какие системы они используют без подсказки.

---

# 71. НЕЛЬЗЯ ОБЪЯВЛЯТЬ MVP ГОТОВЫМ ПО ФАКТУ ЗАПУСКА БОТА

Работающий Telegram-бот ≠ MVP.

MVP готов, когда:

```text id="c8m2r7"
WORLD EXISTS
+
PLAYERS ACT
+
WORLD CHANGES
+
PLAYERS NOTICE
+
HISTORY PERSISTS
```

# 73. ЧТО MVP ДОЛЖЕН ДОКАЗАТЬ

Не:

> «Мы можем сделать много систем».

А:

> **«Мы можем создать мир, который интересно наблюдать и изменять.»**

И ещё:

> **«История возникает не только из заранее написанного сюжета, а из взаимодействия игроков, NPC, информации, событий и состояния мира.»**

---

# 74. ФИНАЛЬНЫЙ ПРИНЦИП

MVP WORLD//ERROR должен быть маленьким по размеру, но настоящим по архитектуре.

```text id="v8q3m1"
SMALL WORLD
+
REAL STATE
+
REAL TIME
+
REAL PLAYERS
+
REAL CONSEQUENCES
+
REAL HISTORY
```

Лучше:

```text
6 локаций
10 NPC
5 игроков
```

которые создают непредсказуемую историю,

чем:

```text
500 локаций
1000 NPC
```

которые существуют только в базе данных.

# 75. ФИНАЛЬНАЯ ФОРМУЛА MVP

```text id="k4m9q2"
ONE CHAT
      ↓
ONE WORLD INSTANCE
      ↓
PERSISTENT WORLD STATE
      ↓
PLAYERS
      ↓
ACTIONS
      ↓
EVENT ENGINE
      ↓
CONSEQUENCES
      ↓
INFORMATION
      ↓
ASYMMETRIC KNOWLEDGE
      ↓
INVESTIGATION
      ↓
WORLD CHANGES
      ↓
HISTORY
      ↓
PLAYERS RETURN
      ↓
WORLD IS DIFFERENT
```

Если эта система работает, WORLD//ERROR уже существует в своей главной форме.

Всё остальное — расширение.

> **MVP должен не показать весь WORLD//ERROR.
> Он должен доказать, что WORLD//ERROR способен существовать.**
